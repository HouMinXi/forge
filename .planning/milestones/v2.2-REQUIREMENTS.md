# Forge v2.2 -- Trusted Review Execution: Requirements

## Outlet A: CLI Dispatcher (untrusted/cheap models)

- [ ] **CLI-01**: SKILL.md aggregate detects outlet mode and dispatches to `code-forge review` via Bash tool (not inline self-drive)
- [ ] **CLI-02**: On missing auth or CLI failure, SKILL.md reports error and STOPS -- never silently degrades to self-drive (FAIL CLOSED)
- [ ] **CLI-03**: `code-forge review` auto-detects project toolchain (py_compile/ruff/pytest for Python; extensible) when no tools.yaml exists
- [ ] **CLI-04**: First-run auto-init generates minimal gate.yaml + tools.yaml from detected toolchain -- user sees zero config on first use
- [ ] **CLI-05**: Fail-fast reachability probe verifies the CONFIGURED review backend is callable (non-interactive, returns within a bounded time) before starting the review pipeline. The probe MUST be backend-agnostic -- per backend type: an `api` backend (OpenAI/Anthropic format) checks its configured `api_key_env` is present (optional cheap liveness); a `cli` backend (e.g. `claude -p`, `aicc`) runs that CLI's own auth check (e.g. `claude auth status`). The exact mechanism is determined by the Phase 5 verification, NOT assumed here. See BACKEND-01
- [ ] **CLI-06**: Each review pass runs as a fresh backend invocation owned by Python -- a fresh subprocess for `cli` backends, a fresh HTTP request for `api` backends -- so the editor's executor model cannot fabricate results (mechanical cycle counting; pipeline exists, wire to editor entry)
- [ ] **CLI-07**: Subprocess orphan protection for `cli` backends: process group management + signal handlers to prevent leaked review subprocesses (e.g. `claude -p`, `aicc`) on cancel/timeout. `api` backends cancel the in-flight HTTP request instead
- [ ] **CLI-08**: Post-review cost summary displays total token usage and estimated cost from the backend response (token counts from the `api` response body or the `cli` output)
- [ ] **CLI-09**: SKILL.md reads state.json after CLI exits to report findings -- no stderr parsing

- [ ] **BOTH-01**: Pass prompt includes "systematically cover the whole diff risk surface" instruction to reduce focused-not-broad gap
- [ ] **BOTH-02**: Backend configuration (`FORGE_BACKEND`, per-backend `model` + `api_key_env`) + auth documented with VS Code / Cursor / PyCharm guide
- [ ] **BOTH-03**: Worktree cwd validation: `code-forge review` verifies it is running inside a linked worktree (not main tree) before starting
- [ ] **BOTH-04**: Outlet selection logic: explicit override (env var / flag) wins. With no override, select by OBJECTIVE signal only -- the CONFIGURED review backend's reachability (Outlet A needs a reachable backend; Outlet B does not). Fail-safe default = Outlet A (CLI, mechanical enforcement). NEVER auto-detect "model capability": a model cannot reliably self-assess whether it is trustworthy (that unreliability is the entire reason Reviewer Canary exists), and letting a weak model self-rate would route it into inline self-drive -- reproducing the exact failure v2.2 removes

## Pluggable Review Backend

- [ ] **BACKEND-01**: The review backend is pluggable, NOT hard-bound to `claude`. Forge supports two HTTP API wire formats -- OpenAI-format (`POST /v1/chat/completions`, `Authorization: Bearer`) and Anthropic-format (`POST /v1/messages`, `x-api-key`) -- plus a `cli` backend type that wraps an existing review CLI (`claude -p` to use a Claude subscription without an API key, or `aicc` to reuse a multi-provider setup). Backends are config entries `{name, type, format?, base_url?, api_key_env?, model}`; API keys are referenced by env-var name (`api_key_env`), NEVER stored inline. Provider/model selection is config-driven (`FORGE_BACKEND` env override > config default). The DEFAULT backend (no config) is the main session model -- concretely a plain `claude -p` invocation using the user's default Claude model; the user explicitly configures any alternative, and forge NEVER auto-selects a model by analyzing the diff (code complexity, change size, or any added dimension). The anti-fake property (Python owns each pass + counts cycles) holds for both `api` (HTTP) and `cli` (subprocess) backends. Phase 5 locks the backend-config abstraction + backend-agnostic reachability probe; the adapter implementations land in Phase 7.

## Out of Scope

- Modifying standalone pass skills (qodo-review, code-review-expert, adversarial-qe) -- hard constraint
- Model depth capability (pin-Opus limited by token cost) -- requires cost-control milestone
- M2 risk-graded review depth (complexity-based model routing) -- follows Path A, since Path A turns each review into real API spend. Forge does NOT analyze the diff to pick a model for the user (no complexity / change-size routing) -- the user configures the model and forge follows the session model by default. Diff-driven model routing stays a deferred, opt-in-only M2 concern, never a default behavior
- M3 product repositioning -- opposite direction from user's goal
- Agentic review depth (anti-feature per research: incompatible with forge's fixed-pipeline thesis)

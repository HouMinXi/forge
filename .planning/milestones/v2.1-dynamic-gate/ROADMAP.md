# Forge v2.1 -- Dynamic Gate Backport: ROADMAP

**Milestone:** v2.1 (dynamic-gate)
**Status:** Planned -- spec converged (v3.2; 3 review rounds: 6-way -> host
ground-truth -> 5-view re-review)
**Spec:** ./SPEC.md (full R1-R5 requirements, key decisions, motivation)
**Depends on:** v2.0 (state machine, shipped d65d2f7)
**Planning split:** host writes this ROADMAP + exit criteria; detailed per-phase
PLAN.md is generated by `/gsd-plan-phase` in a sub-session.

## One-line goal

Close forge's own blind spot -- a marker-trusting commit gate that runs no tests,
plus mock-only coverage that misses integration bugs -- by adding dynamic gates
(a real test commit gate, a mutation pipeline step, e2e coverage). Forge applies
its own anti-hallucination thesis: verification grounding beats prompt-only
self-claim.

## Requirements (full text in SPEC.md)

- **R1** -- verification commit gate: a REAL `.git/hooks/pre-commit` (not the
  bypassable PreToolUse hook) that runs the test suite via `forge gate-check`
  and blocks on NEW failures vs a baseline.
- **R2** -- mutation as a review-pipeline step (NOT a commit gate):
  `source="MUTANT"` + `l2_runner`, Python mutmut, LOCAL-sync / CI-async.
- **R3** -- integration/e2e coverage: heuristic checklist + opt-in
  `.forge/components.yaml`.
- **R4** -- gate-philosophy docs: fill the empty CLAUDE.md:287-288 sections.
- **R5** -- test layering (DEFERRED to the forge-code phase): threshold-triggered
  real-dependency regression.

## Key decisions (round-3; full rationale in SPEC.md)

- **FAIL-OPEN guard:** gate-check's OWN config/parse errors -> BLOCK, isolated
  from the test command's exit codes (forge's EXIT_CLI_ERROR=2 must not be
  mistranslated to ALLOW).
- **exit-code translation:** test 1 / 4 / 5 / timeout -> hook BLOCK; test 2-3 ->
  hook 0 + stderr warning.
- **install-hooks:** resolve the hooks dir via `git rev-parse --git-path hooks`;
  embed the ABSOLUTE forge path (hooks run off-PATH).
- **CI detection:** FORGE_MODE=ci plus CI / GITHUB_ACTIONS / GITLAB_CI /
  JENKINS_URL / BUILD_URL.
- **baseline:** its own domain (not the 02-03 finding-baseline); bootstrap =
  first-run allow + warn.

## Phases and Exit Criteria

These exit criteria are this ROADMAP's main contribution. Forge historically
shipped without standardized success criteria (see MILESTONES.md v2.0 note).
They encode the host-acceptance ground-truth standard proven on plan-forge: not
"tests pass" but "tests have teeth (bug-inject) AND the real integration path
runs (real-dependency smoke, not a mock)". `/gsd-plan-phase` expands each phase
into a detailed PLAN.md; these criteria are the per-phase gate that PLAN.md must
satisfy.

### Phase 0 -- config bootstrap (gate.yaml + baseline)

**Goal:** create forge's own `.forge/gate.yaml` and an initial test baseline so
R1 can dogfood without a chicken-and-egg deadlock. Config only, no logic.

**Exit Criteria:**
1. `.forge/gate.yaml` valid: `test.command=["python3","-m","pytest","tests/","-q"]`,
   `test.env={PYTHONPATH: "src"}`, `test.timeout_seconds`, `test.cwd`; yamllint
   clean.
2. `.gitignore` gains `!.forge/gate.yaml` -- without it the file is uncommittable
   (`.forge/*` is ignored, only `tools.yaml` is currently excepted).
3. test baseline generated: the 521 tests run, `known_failures` recorded in
   `.forge/test_baseline.json` with a schema documented for the Phase-1
   gate-check to consume; the baseline file stays gitignored (generated data).
4. a `# config` commit, human-voice message, ASCII-clean, no AI traces.
5. proven load-bearing: bare `python3 -m pytest` fails (44 import errors) and
   `PYTHONPATH=src` passes (521) -- this is why `test.env` exists.

### Phase 1 -- R1 (commit gate) + R4 (docs)

**Goal:** a real test commit gate (`gate-check` CLI + pre-commit hook +
`install-hooks`) and the gate-philosophy docs.

**Exit Criteria:**
1. Step 0: ruff clean, non-ASCII grep clean on every changed file.
2. `forge gate-check`: parses gate.yaml, runs the test command with `test.env`,
   translates exit codes (test 1/4/5/timeout -> BLOCK; 2-3 -> warn); gate-check's
   OWN errors (gate.yaml missing / parse / unsafe command) -> BLOCK, never the
   warn path (FAIL-OPEN guard).
3. real `.git/hooks/pre-commit` gates on source files in `git diff --cached
   --name-only`; `forge install-hooks` resolves the dir via `git rev-parse
   --git-path hooks`, embeds the absolute forge path, backs up + chains an
   existing hook, and ABORTS when core.hooksPath is set.
4. CI detection: FORGE_MODE=ci + the platform vars; FORGE_SKIP_TESTS ignored in
   CI.
5. baseline: blocks only NEW failures vs `.forge/test_baseline.json`; no baseline
   -> allow + warn; a new failing test absent from the baseline -> BLOCK.
6. full suite green + NEW unit tests for gate-check / exit-code translation /
   install-hooks.
7. bug-inject (teeth): break the exit-code translation (e.g. map test-1 to
   hook-0) -> a gate-check test FAILS; revert -> PASS. Same for the FAIL-OPEN
   guard. Mock-only tests that never exercise the real hook do not count.
8. real-dependency smoke (ground-truth): commit a deliberately-red tree -> the
   hook BLOCKS; a terminal (non-Bash) commit of the same tree -> still gated; a
   missing/broken gate.yaml -> BLOCK (not FAIL-OPEN). Drive the real hook, not a
   mock.
9. forge's OWN three-cycle review (the pipeline forge ships) reaches zero
   findings.
10. R4: the CLAUDE.md:287-288 "What Forge Covers" + "What Forge Is Missing"
    sections are filled (static passes are one layer, backed by dynamic gates;
    passes-count is not a quality guarantee).

**Dogfood:** uses Phase 0's gate.yaml; once R1 lands, forge's own commits are
gated by R1.

### Phase 2 -- R2 (mutation pipeline step)

**Goal:** mutation as a state-machine step, not a commit gate.

**Exit Criteria:**
1. Step 0 clean.
2. `StateFinding.source` gains `"MUTANT"` (additive to `Literal["L0","L1"]`);
   `l2_runner` wired after the L1 phase.
3. LOCAL: a fast diff-scoped mutmut run is synchronous, a survivor resets the
   cycle; CI: async, fails the build, does NOT reach the cycle counter.
4. unsupported language -> a visible MUTATION_SKIPPED finding; flaky-guard (3x
   baseline) aborts mutation on a flake.
5. full suite green + NEW tests for the l2_runner + source="MUTANT" path.
6. bug-inject (teeth): add a toothless test (passes regardless of impl) ->
   mutation surfaces a survivor -> the phase flags it; remove it -> clean.
7. mutation dogfood: mutate forge's own code changed in this phase, confirm
   forge's tests kill the mutants (a survivor is a real coverage gap).
8. three-cycle review zero findings.

### Phase 3 -- R3 (e2e coverage)

**Goal:** integration/e2e heuristic + opt-in config.

**Exit Criteria:**
1. Step 0 clean.
2. heuristic: a diff spanning >= 2 source dirs with a changed signature -> a
   non-blocking checklist finding.
3. opt-in `.forge/components.yaml`: a diff on two components sharing a data path
   with no e2e test -> a P2 finding.
4. full suite green + NEW tests for both layers.
5. bug-inject (teeth): a cross-component change with no e2e test -> the
   checklist/P2 fires; add the test -> it clears.
6. three-cycle review zero findings.

## Reference Class

Three comparable multi-dynamic-gate projects with plan-vs-actual implementation
ratios and lessons:

- Chromium CQ tiering (2018-present): diff-based CI tier selection (which builders
  to run based on affected files). Integration: estimated ~1.5x planned. The
  directory-to-builder mapping was straightforward; shared-header impact radius was
  the long tail. Lesson: shared dependencies are the hard case, not leaf components.

- Rust bors / pre-merge queue (2015-present): serialized merge queue that runs the
  full test suite before merging. Pre-merge execution is the correct design for
  preventing regressions; the tradeoff is queue serialization. Ratio: ~1.2x planned
  (estimated). Lesson: pre-merge gates are load-bearing; post-merge revert-first
  policies are the escape hatch, not the primary design.

- Forge Phase 1 (internal reference): commit gate + install-hooks. Four plans,
  estimated 5 days, actual 7 days including reviews = ratio 1.4x. Main overrun:
  EC-9 review found 11 additional findings; the install_hooks backup-conflict bug
  added unplanned fix work. Lesson: review is the long tail, not implementation.

## Risks

### Known Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Phase 1 bug lands on main and breaks Phase 2 dogfood | Medium | High | worktree-per-phase + host ground-truth verification before merge (D-04) |
| Dogfood chicken-and-egg: gate-check must pass before it can gate itself | High (first run) | Medium | Phase 0 baseline bootstrap; first run allows with warning |
| mutmut not installed; R2 mutation dogfood cannot run | High (env-specific) | Low | D-05: soft dependency, emits MUTATION_SKIPPED; does not block Phase 2 merge |

### Gray Rhinos

| Risk | Denial Reason | Counter |
|------|--------------|---------|
| Review overhead dominates implementation (>3x ratio) | "Three-cycle review is the product, not overhead" | circuit-break on non-convergence; single-model converges what a panel spins on |
| R1 gate bypassed via FORGE_SKIP_TESTS in CI | "Dev envs need escape hatches" | FORGE_SKIP_TESTS is local-only; CI mode always runs regardless (SPEC-locked) |

### Black Swans

| Risk | Survival Plan |
|------|--------------|
| Phase 1 gate-check bug blocks all forge commits on main | revert gate-check to pass-through; restore from worktree; reapply with fix |
| All three phases ship but equivalent mutants cause engineers to ignore mutation findings | document equivalent mutant limitation in CLAUDE.md; classify survivors as CONFIRMED (review-worthy), not hard failures |

## Pre-mortem

Imagine the v2.1 milestone ships and the dynamic gates fail to work in practice.
The most likely causes:

1. R1 lands but the gate is silently bypassed in CI via FORGE_MODE or env vars.
   Early warning: CI builds show no gate-check output in logs; a deliberately-red
   tree is merged without blocking. Counter: CI detection is SPEC-locked (FORGE_MODE
   + platform vars); FORGE_SKIP_TESTS is explicitly rejected in CI mode.

2. R2 lands but equivalent mutants flood the review with CONFIRMED findings that
   engineers cannot action. Early warning: review loops never converge because a
   new MUTANT survivor appears every round. Counter: consecutive_survivor_rounds
   hard-stops at 3; MUTANT findings are CONFIRMED (human triage), not EXIT_FAIL
   (not a commit blocker).

3. R3 components.yaml is too painful to author for code/kernel/networking (106
   subsystems). Early warning: the first real components.yaml takes >1 day to
   write. Counter: auto-detection workflow documented; Layer 1 is non-blocking and
   still fires without components.yaml.

4. Phase 0 baseline becomes stale after tests are added or removed; gate-check
   blocks clean trees. Early warning: gate-check blocks a commit that adds a new
   test. Counter: baseline is regenerated by re-running Phase 0 bootstrap; the
   schema documents the regeneration command.

5. The three-cycle review itself becomes the bottleneck: review takes longer than
   implementation. Early warning: a single 15-line fix triggers 1h+ review without
   convergence. Counter: single-model review converges what a multi-model panel
   spins on; circuit-break at 3 non-converging rounds.

| Stressor | Response | Classification |
|---------|----------|----------------|
| gate.yaml missing after repo clone | gate-check BLOCKS with explicit error ("gate.yaml not found -- run forge gate-check --init"); does not silently allow | survive |
| mutmut hangs during Phase 2 dogfood | timeout guard kills subprocess; emit MUTATION_SKIPPED (DISMISSED); review continues; commit not blocked | survive |

## Scope Challenge

Q1: Does this need to exist?
Yes. Forge ships the thesis "verification grounding beats prompt-only self-claim"
while its own commit gate ran no tests (marker-trusting blind spot). The specific
cost of doing nothing: CLAUDE.md honest assessment section explicitly states "until
R2 and R3 land, forge is partially implementing its own thesis." This is a
self-contradiction that is visible to every user who reads the docs.

Q2: Three real consumers
- Forge itself: dogfood -- forge's own commits are gated by R1, mutation-checked
  by R2, and cross-component-checked by R3.
- plan-forge: uses the forge review pipeline; R2 adds mutation coverage on
  plan-forge's own changed files.
- Any project running forge review with a .forge/gate.yaml: gets the real commit
  gate and mutation pipeline without additional configuration.

Q3: Do-nothing cost
Doing nothing + documenting the gap: forge continues to ship the verification
grounding thesis while its own commit gate relies on a self-claim marker. The
honest assessment in CLAUDE.md documents this explicitly. The cost is reputational:
a tool that argues verification grounding > self-claim while not applying its own
standard to itself.

Q4: Barbell vs middle ground
Barbell options: (A) static review only, no dynamic gates (status quo, documented
gap); (B) full automated test generation + mutation + full e2e call-graph analysis
(years of work, unsolved for shell/C). R1+R2+R3 is NOT the middle ground -- it IS
the minimal viable dynamic gate set that closes the specific blind spot (no-test
commit gate) without the unsolved problems (call-graph extraction, cross-repo
impact). Function-level mutation scoping and cross-repo impact are incremental
enhancements.

## External Voices

Primary sources on dynamic gate design and mutation testing in practice:

- Petrovic & Ivankovic (2018). State of Mutation Testing at Google. ICSE 2018.
  Documents Google's deployment of mutation testing to ~6,000 engineers who author
  or review code, affecting over 13,000 code authors (roughly 30% of all diffs).
  Key findings: diff-scoped mutation is the enabling design decision for CI
  practicality; results integrated into code review workflow, not a separate async
  gate; engineer acceptance requires framing surviving mutants as actionable
  suggestions, not failures. Primary real-world reference for the diff-scoped design
  in forge R2.

- Jia & Harman (2011). An Analysis and Survey of the Development of Mutation
  Testing. IEEE Transactions on Software Engineering, Vol. 37, No. 5. The
  most-cited comprehensive survey on mutation testing. Documents the long-standing
  adoption challenge: equivalent mutants produce false positives, making
  mutation-adequate tests hard to achieve in practice.

A legitimate objection exists: the Jia & Harman survey documents that equivalent
mutants are a fundamental unsolved problem. A surviving mutant may indicate a test
weakness OR an equivalent mutant -- the reviewer cannot distinguish them
automatically. Critics argue this reduces actionability. Forge mitigates by
classifying survivors as CONFIRMED (review-worthy, not blocking commits) rather
than hard CI failures.

Historical lesson from Petrovic & Ivankovic (2018): early internal pilots of
mutation at Google without diff-scoping produced runs too slow to be actionable.
The retrospective lesson: selective (diff-scoped) mutation was the enabling design
decision. Forge R2 inherits this constraint as a first-principles design
requirement, not an optimization.

## Summary

Phase 19.1 converts documentation-level checklists into unfakeable external
gates. The core insight is cost-class splitting: checkpatch (seconds) runs at
commit time via forge's generated pre-commit hook; vng (minutes) runs at send
time via content-hashed receipts in a personal dotfiles hook. Two repos are
involved: forge (PUBLIC, product code) and dotfiles (bare repo, personal
hooks). The boundary is strict: forge owns commit-time checkpatch + non-ASCII +
AI-vocab preset generation in `install_hooks.py`; dotfiles owns the vng receipt
wrapper and send-time PreToolUse hook.

The existing `install_hooks.py` generates a pre-commit shell script with a
non-code carve-out and a `code-forge verify` attestation check, then delegates
to `code-forge gate-check`. The kernel-tree preset (checkpatch re-run +
non-ASCII + AI-vocab grep) must be injected into this generated script as a new
block that fires when `scripts/checkpatch.pl` exists at repo root, before the
existing `gate-check` invocation. The gate.yaml schema needs a `checkpatch`
section for flag customization and explicit opt-out.

Two additional trivial deliverables: fix SKILL.md line 176 overclaim (narrow
"ALL output" to "code, comments, and commit messages") and strip D-NN plan-ref
labels from test_fixval.py lines 32, 89, 650.

**Primary recommendation:** Extend `generate_hook_content()` with a kernel-tree
detection block that auto-runs checkpatch + non-ASCII + AI-vocab when
`scripts/checkpatch.pl` is present, reads optional flags from gate.yaml, and
fail-closes with `--strict --max-line-length=80` as default.

### Pattern 1: Kernel-Tree Preset Block in Generated Hook

**What:** A shell block injected into the generated pre-commit hook that
detects kernel trees and runs checkpatch + non-ASCII + AI-vocab.
**When to use:** When `scripts/checkpatch.pl` exists at repo root.

```bash
# Source: install_hooks.py generate_hook_content() -- new block
# kernel-tree preset: checkpatch + non-ASCII + AI-vocab
if [ -x "scripts/checkpatch.pl" ]; then
    # Load optional flags from gate.yaml
    CHECKPATCH_ENABLED=true
    CHECKPATCH_FLAGS="--strict --max-line-length=80"
    if [ -f ".code-forge/gate.yaml" ]; then
        _cp_enabled=$(python3 -c "
import yaml, sys
try:
    with open('.code-forge/gate.yaml') as f:
        d = yaml.safe_load(f)
    cp = d.get('checkpatch', {}) if d else {}
    if cp.get('enabled') is False:
        print('false')
    else:
        flags = cp.get('flags', '')
        if flags:
            print(flags)
        else:
            print('default')
except Exception:
    print('default')
" 2>/dev/null)
        case "$_cp_enabled" in
            false) CHECKPATCH_ENABLED=false ;;
            default) ;;  # use defaults
            *) CHECKPATCH_FLAGS="$_cp_enabled" ;;
        esac
    fi

    if [ "$CHECKPATCH_ENABLED" = "true" ]; then
        echo "code-forge: running checkpatch.pl on staged diff..." >&2
        git diff --cached | scripts/checkpatch.pl $CHECKPATCH_FLAGS - || {
            echo "code-forge: checkpatch FAILED -- fix before committing" >&2
            exit 1
        }
    else
        echo "code-forge: checkpatch explicitly disabled via gate.yaml" >&2
    fi

    # non-ASCII check on staged diff + commit message
    _non_ascii=$(git diff --cached -U0 | grep '^+' | grep -P '[^\x00-\x7F]' | head -5)
    if [ -n "$_non_ascii" ]; then
        echo "code-forge: non-ASCII characters in staged diff:" >&2
        printf '%s\n' "$_non_ascii" >&2
        exit 1
    fi

    # AI-vocab check on staged diff
    _ai_vocab=$(git diff --cached -U0 | grep '^+' | grep -iE \
        'delve|tapestry|testament|moreover|furthermore|it is worth noting|comprehensive|robust|leverage|utilize|facilitate|seamless|paradigm|holistic|ensuring|notably|importantly|crucial|vital' \
        | head -5)
    if [ -n "$_ai_vocab" ]; then
        echo "code-forge: AI vocabulary detected in staged diff:" >&2
        printf '%s\n' "$_ai_vocab" >&2
        exit 1
    fi
fi
```

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| YAML parsing in generated shell | Shell YAML parser | python3 -c with PyYAML (minimal inline) | Shell YAML parsing is fragile; PyYAML already a dep |
| Content hashing | Custom hash function | sha256sum (coreutils) | Standard, deterministic, already available |
| Kernel tree detection | Path list / hardcoded repos | `[ -x "scripts/checkpatch.pl" ]` | Generalizes to any kernel tree without config |
| Non-ASCII detection | Custom character scanner | `grep -P '[^\x00-\x7F]'` | Proven pattern from linux-net-next/CLAUDE.md |
| Checkpatch output parsing | Custom parser | Existing `parsers/checkpatch.py` (for forge review) | Already handles the emacs format; commit-gate uses raw exit code |

**Key insight:** The commit-time gate does NOT need to parse checkpatch output
into Finding objects. It only needs the exit code (0 = clean, non-0 = block).
The existing `parsers/checkpatch.py` is for forge's review pipeline, not for
the pre-commit hook. The hook is a shell script that runs checkpatch and checks
`$?`. Keep it simple.

## Common Pitfalls

### Pitfall 1: Fail-Open on Missing Config
**What goes wrong:** If gate.yaml has no `checkpatch` section and the code
treats missing-config as "skip checkpatch", the gate is fail-open -- the exact
disease this phase cures.
**Why it happens:** Natural programming instinct: "no config = no action".
**How to avoid:** D-09 mandates fail-closed: missing config = run with defaults
(`--strict --max-line-length=80`). Only an explicit `checkpatch.enabled: false`
skips the run.
**Warning signs:** Any code path where `scripts/checkpatch.pl` exists but
checkpatch does not run AND there is no explicit opt-out in gate.yaml.

### Pitfall 2: Non-Code Carve-Out Bypass
**What goes wrong:** The non-code carve-out (D-10) must skip checkpatch for
`# docs`/`# chore`/`# wip` commits. But the carve-out is at the TOP of the
generated hook (line 186-200 in current install_hooks.py). If the kernel preset
block is placed AFTER the carve-out, it correctly inherits the skip. If placed
BEFORE, non-code commits would still run checkpatch.
**Why it happens:** Wrong insertion point in generate_hook_content().
**How to avoid:** Insert the kernel preset block AFTER the existing carve-out
block and AFTER the attestation block, but BEFORE the `exec code-forge
gate-check` line. This way, non-code commits exit 0 at the carve-out and never
reach the kernel preset.
**Warning signs:** A `# docs` commit in a kernel tree runs checkpatch.

### Pitfall 3: Stale Receipt After Rebase
**What goes wrong:** After `git rebase`, the base commit SHA changes but the
patch content may be identical. If the receipt key only hashes patch content,
stale receipts survive a rebase.
**Why it happens:** Incomplete hash input.
**How to avoid:** D-05 specifies the key = sha256(patch content + base commit
SHA). Both must be in the hash. Rebase changes base SHA = old receipt invalid.
**Warning signs:** `vng-receipt` passes after a rebase without re-running vng.

### Pitfall 4: Commit Message Not Checked by Pre-Commit Hook
**What goes wrong:** `git diff --cached` only shows staged file changes, not the
commit message. The commit message is not yet written when pre-commit runs.
**Why it happens:** Git's hook execution order: pre-commit fires before the
message is composed (commit-msg hook fires after).
**How to avoid:** For commit-message AI-vocab/non-ASCII checking, either:
(a) use a `commit-msg` hook (separate from pre-commit), or
(b) rely on the personal PreToolUse hook (D-03) which sees the `git commit -m`
command string. The forge pre-commit hook checks staged diff content; the
personal hook checks the message. This layered approach (D-04) covers both.
**Warning signs:** AI vocabulary in a commit message is not caught by the
pre-commit hook alone.

### Pitfall 5: Two-Repo Confusion
**What goes wrong:** Personal hook code (vng-receipt, check_vng_receipt.sh)
accidentally committed to the forge PUBLIC repo, or forge product code
accidentally committed via the dotfiles bare repo.
**Why it happens:** Working in both repos in the same session.
**How to avoid:** Strict separation: forge changes go through GSD workflow
with worktree discipline; personal hooks go through `git --git-dir=$HOME/.dotfiles
--work-tree=$HOME`. Verify with `git status` in each repo before committing.
**Warning signs:** `git diff --name-only` in forge shows files under `~/.claude/`.

### Pitfall 6: checkpatch.pl stdin vs file mode
**What goes wrong:** checkpatch.pl has different behavior when reading from
stdin (`-`) vs a file (`--patch file.patch`). The `--patch` flag is needed for
file mode; stdin mode does not need it.
**Why it happens:** checkpatch.pl CLI quirks.
**How to avoid:** The pre-commit hook pipes `git diff --cached` to checkpatch
via stdin. Use `scripts/checkpatch.pl $FLAGS -` (the trailing `-` means stdin).
The existing `runner.py` (line 12) notes that checkpatch requires stdin input.
**Warning signs:** "no input files specified" error from checkpatch.

### Example 3: vng-receipt Wrapper Skeleton

```bash
#!/bin/bash
# vng-receipt: wrapper that tees vng output to a content-hashed receipt
# Usage: vng-receipt run <vng-args>
set -euo pipefail

RECEIPT_DIR=".vng"

usage() {
    echo "Usage: vng-receipt run <vng-args>" >&2
    exit 1
}

[ "${1:-}" = "run" ] || usage
shift

# Compute receipt key from current patch + base
PATCH_CONTENT=$(git diff HEAD)
BASE_SHA=$(git rev-parse HEAD)
RECEIPT_KEY=$(printf '%s%s' "$PATCH_CONTENT" "$BASE_SHA" | sha256sum | cut -d' ' -f1)

mkdir -p "$RECEIPT_DIR"

# Run vng, tee output
TMPOUT=$(mktemp)
trap 'rm -f "$TMPOUT"' EXIT

if vng "$@" 2>&1 | tee "$TMPOUT"; then
    STATUS="PASS"
    RC=0
else
    STATUS="FAIL"
    RC=$?
fi

# Write receipt
cat > "$RECEIPT_DIR/$RECEIPT_KEY.receipt" << EOF
status=$STATUS
exit_code=$RC
timestamp=$(date -u +%Y-%m-%dT%H:%M:%SZ)
base=$BASE_SHA
patch_hash=$(printf '%s' "$PATCH_CONTENT" | sha256sum | cut -d' ' -f1)
vng_args=$*
EOF

exit $RC
```

## Open Questions (RESOLVED)

1. **Commit message checking timing**
   - What we know: pre-commit hook fires before the message is composed.
     commit-msg hook fires after. Personal PreToolUse hook (D-03) sees the
     `git commit -m "..."` command string.
   - What's unclear: Should forge generate BOTH a pre-commit AND a commit-msg
     hook? Or rely solely on the personal PreToolUse hook for message checking?
   - Recommendation: The personal hook (D-03) covers the commit message. The
     forge pre-commit hook covers staged diff content. Do not generate a
     commit-msg hook -- it adds complexity for a gap already covered. D-04
     explicitly defines this two-layer approach.

2. **gate.yaml checkpatch section validation**
   - What we know: gate_check.py has load_gate_config() that validates the
     `test` section. A new `checkpatch` section needs validation.
   - What's unclear: Should validation live in gate_check.py (alongside test
     validation) or in install_hooks.py (at generation time)?
   - Recommendation: Validate at BOTH times. install_hooks.py reads gate.yaml
     at hook generation to decide whether to emit the kernel preset block.
     The generated hook reads it again at commit time for runtime flags. The
     Python-side validation (install_hooks.py) catches schema errors early;
     the shell-side parsing is minimal (just reads enabled + flags).

3. **`.vng/` gitignore**
   - What we know: `.vng/` is not in any gitignore currently. D-06 says
     "gitignored".
   - What's unclear: Should the vng-receipt wrapper auto-add `.vng/` to
     `.gitignore`, or should the user do it manually?
   - Recommendation: The vng-receipt wrapper should check and auto-append
     `.vng/` to `.gitignore` on first run (if not already present). This is
     standard practice for tool-generated directories.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Malicious gate.yaml disables all checks | Tampering | Fail-closed default (D-09); explicit opt-out logged to stderr |
| Shell injection via gate.yaml flags field | Elevation | Validate flags are simple --flag=value patterns; no shell metacharacters |
| Receipt forgery (hand-write .vng/*.receipt) | Spoofing | Content hash ties receipt to exact patch+base; forging requires knowing the hash key formula AND producing matching content |

**Note on gate.yaml trust:** The existing SEC-01 trust gate (Phase 17) already
handles repo-supplied gate.yaml credential exfil. The checkpatch `flags` field
is a new attack surface: a hostile repo could set `flags: "; rm -rf /"`. The
generated hook must validate that flags contain only `--word` and `--word=value`
patterns (no shell metacharacters). This reuses the same `SHELL_METACHARACTERS`
set from gate_check.py:validate_command_safety().

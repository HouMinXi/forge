  <action>
Create the docs/design/ directory if it does not exist. Write the design specification document at docs/design/reviewer-canary-spec.md.

The document MUST contain ALL of the following sections (use Markdown ## headings). Each section's required content is specified below.

SECTION 1 -- Problem Statement:
Define the problem: an LLM reviewer can fabricate a "clean" verdict without examining the diff. The anti-shirk receipt protocol (Phase 4, v2.1) proves the pipeline ran, but does not prove the reviewer read the code. Canary closes this gap. Reference the deleted check #8 that SPEC-01 supersedes and explain why canary is stronger: check #8 was a marker-in-code pattern (the reviewer could learn to look for the marker without analyzing the surrounding code); canary is a planted-defect-in-diff pattern that requires genuine code comprehension.

SECTION 2 -- Design Anchors (Locked Constraints):
Quote these four design anchors by ID and state them as non-negotiable implementation constraints:
- D-16 from 05-CONTEXT.md: "NEVER auto-detect model capability. A model cannot reliably self-assess trustworthiness -- that unreliability is the reason Reviewer Canary exists."
- D-25 from 05-CONTEXT.md: "The anti-fake property (Python owns each pass + counts cycles + canary) holds for both api and cli backends."
- D-26 from 05-CONTEXT.md: "Trust vs depth are orthogonal. Canary validates reviewer ATTENTION, not model strength."
- BOTH-04 from REQUIREMENTS.md: Outlet selection uses ONLY objective signals, never model self-assessment.
- State these as non-negotiable constraints that the implementation MUST satisfy.

SECTION 3 -- Canary Injection Mechanism:
- WHERE: injection happens in Python BEFORE the L1 provider prompt reaches the backend. Concretely, between _execute_round calling _run_l1_phase (machine.py line 628) and the l1_provider() invocation (machine.py line 516). Python modifies the diff/prompt payload to include a synthetic defect.
- HOW: Python constructs a synthetic diff hunk containing a known, unambiguous defect. The hunk uses a synthetic file path (e.g., _canary_NNN.py) so it does not collide with real files. The canary is tagged with an internal canary_id (UUID4) that the reviewer never sees.
- WHEN: configurable per-round probability via FORGE_CANARY_RATE env var (float 0.0-1.0, default 1.0). Injection is deterministic when rate is 1.0.
- SCOPE: injection is prompt-only, NEVER file-write. No working tree mutation, no git history contamination.
- BACKEND-AGNOSTIC: per D-25, injection happens above the backend layer, so it works identically for api and cli backend types.

SECTION 4 -- Defect Types:
Enumerate at least 6 concrete canary defect categories. For each provide: category name, a concrete Python code example (the synthetic snippet), what a competent reviewer MUST flag, and difficulty rating (easy/medium/hard). Required categories:
(a) Hardcoded secret -- easy
(b) Unchecked None dereference -- easy
(c) Off-by-one in loop boundary -- medium
(d) SQL injection via string concatenation -- medium
(e) Resource leak (file/connection not closed) -- medium
(f) Silent exception swallowing (bare except: pass) -- easy

SECTION 5 -- Canary Finding Matching:
After L1 returns StateFinding candidates, Python scans for findings whose file path matches the synthetic canary path (_canary_NNN.py). Matching is by file path prefix (deterministic, not fuzzy). The matched canary finding is REMOVED from the findings list before falsification and before _merge_findings -- it must never enter state.json or affect consecutive_clean_rounds.

SECTION 6 -- Disqualification Criteria:
- MISS definition: L1 returns zero findings matching the canary file path.
- LOCAL mode consequence: round's L1 findings are ALL discarded (unreliable), round does NOT count toward consecutive_clean_rounds, infra_error appended with canary_id and round_index.
- CI mode consequence: same as LOCAL plus verdict forced to FAIL.
- Per-round scope: disqualification applies to the round, not permanently. Next round re-injects a new canary.
- State tracking: State dataclass gains canary_results: list[dict] with fields canary_id, defect_type, injected (bool), detected (bool), round_index.

SECTION 7 -- Integration Points:
Map to real codebase identifiers:
- machine.py _execute_round (line ~617): inject canary before _run_l1_phase; check match after _run_l1_phase returns, before _merge_findings.
- machine.py StateMachine dataclass: add canary_injector callable field (dependency-injected like l1_provider), defaulting to no-op.
- factories.py build_l1_provider (line ~237): document that canary injection interacts with the L1 prompt construction here. The implementer chooses the injection strategy (wrapper vs direct) during v2.3+.
- state.py StateFinding.source: add "CANARY" to the Literal type for internal tracking.
- state.py State: add canary_results field.
- SKILL.md (Outlet B): canary works identically because injection is prompt-level.
- llm_invoke.py: no changes (canary is above this layer).

SECTION 8 -- Canary Defect Library:
Design a canary_library.py module containing parameterized defect templates as frozen dataclasses with fields: defect_type, language, template (str with placeholders), expected_keywords, difficulty. At injection time, Python selects a template (round-robin or weighted random), fills placeholders with plausible names, and constructs the synthetic diff hunk. Library is extensible via gate.yaml canary_defects section (deferred to v2.3+).

SECTION 9 -- Security Considerations:
- No working tree mutation (prompt-only injection).
- canary_id uses UUID4 (unpredictable).
- Defects must be realistic (test code comprehension, not pattern matching).
- FORGE_CANARY_RATE=0.0 disables injection entirely (opt-out).
- The spec document itself being in-repo means a fine-tuned model could learn canary patterns -- mitigated by randomized defect selection from a large library.

SECTION 10 -- Deferred to v2.3+:
List at least 7 deferred items, each with a one-sentence rationale:
(1) Implementation of canary.py and canary_library.py -- this phase is spec-only per ROADMAP.
(2) Canary difficulty progression -- requires telemetry infrastructure.
(3) Multi-canary injection per round -- validate single-canary baseline first.
(4) Canary result telemetry dashboard -- requires reporting infrastructure.
(5) Custom canary defects via gate.yaml -- requires schema extension.
(6) Cross-language canary library -- aligns with deferred multi-language detect.
(7) Outlet B enforcement mode -- trust boundary differs for inline; needs user feedback.
(8) L0 canary -- L0 tools are deterministic parsers, not LLMs; canary tests LLM attention.

SECTION 11 -- Open Questions for Implementation Phase:
List 5-8 questions the implementer must resolve, including:
(a) Wrap l1_provider vs inject at _execute_round level -- tradeoffs of each approach.
(b) Store canary_results in state.json vs separate file -- schema versioning for existing state.json consumers.
(c) Minimum keyword overlap threshold for canary finding match.
(d) How does canary interact with the existing L1 falsification step (falsify_real.py)? Canary findings must be extracted BEFORE falsification, but what if the reviewer bundles canary and real findings in one response?
(e) What is the canary library extension API surface for gate.yaml custom defects?
(f) Performance budget for per-round injection (prompt size increase, round-trip latency).
(g) How to handle canary in multi-language projects where the injected snippet language must match the project.
(h) Failure modes: what if the reviewer finds the canary but misidentifies the defect type? Is that a pass or a miss?

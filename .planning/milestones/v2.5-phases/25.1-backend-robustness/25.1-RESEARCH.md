# Phase 25.1: Backend Robustness - Research

**Researched:** 2026-06-20
**Domain:** LLM invocation reliability, timeout handling, L1 truncation detection
**Confidence:** HIGH

## Summary

Phase 25.1 delivers three separable work items against forge's LLM invocation
layer: (1) a timeout circuit breaker that aborts after N consecutive L1 timeouts
instead of looping indefinitely, (2) a coverage-based false-green guard that
detects truncated L1 responses passing as clean, and (3) a docs sweep of
configuration.md. All three are grounded against live code at main af378f9.

The circuit breaker (D-1) is mechanically straightforward: add an `is_timeout`
flag to `LLMInvokeError`, an in-memory counter on `StateMachine`, and an
`EXIT_TIMEOUT = 6` constant. The L1 truncation guard (D-4) is the more
nuanced piece: the residual false-green path runs through `factories.py`
`_provider()` where `validate_reviewer_json` accepts a response with
`findings==[]` and at least one `code_excerpt` without checking that excerpts
cover every changed file. The guard derives changed files from `diff_text` and
covered files from `code_excerpts`, flagging any gap as INFRA. Path
normalization across three formats (diff `a/b` prefixed, excerpt plain,
cross-repo absolute) is the primary implementation risk.

**Primary recommendation:** Implement D-1 (circuit breaker) and D-4 Option B
(coverage guard) as separate plans. D-4 Option A (stop_reason plumbing) is
additive and can be a third plan if time allows. The docs sweep is independent
and should be its own plan with a docs/config commit marker.

### D-1: Circuit Breaker Data Flow (grounded)

**Error propagation chain (verified against af378f9):**

1. `llm_invoke.py:326` -- `proc.communicate(timeout=timeout_s)` raises
   `subprocess.TimeoutExpired`
2. `llm_invoke.py:329` -- caught, raises `LLMInvokeError("LLM subprocess
   timed out after %ds")` with `is_timeout=True` (NEW)
3. `llm_invoke.py:453` -- API path: `TimeoutError` caught, raises
   `LLMInvokeError("%s backend timed out after %ds")` with `is_timeout=True` (NEW)
4. `factories.py:295` -- `_provider()` catches `LLMInvokeError`, creates
   INFRA `StateFinding` with `id="l1-{pass}-invoke-fail"`
5. `machine.py:572` -- `_run_l1_phase()` receives findings from l1_provider
6. `machine.py:588-589` -- INFRA-source findings are appended directly
   (skip falsification)

**Where the breaker inserts (planner's discretion, recommended approach):**

The breaker counter should live on `StateMachine` as a simple `int` field
(e.g. `_consecutive_l1_timeouts: int = 0`). The check belongs in
`_run_l1_phase()` AFTER `l1_provider()` returns, examining the returned
findings for INFRA findings whose originating error was a timeout. However,
there is a design tension: `_run_l1_phase()` receives `StateFinding` objects,
not the raw `LLMInvokeError`. The `is_timeout` flag lives on the exception,
which `_provider()` catches and converts to a `StateFinding`.

**Two viable approaches to bridge this:**

1. **Convention-based ID matching (simpler):** The INFRA finding created in
   `factories.py:303` has `id="l1-{pass}-invoke-fail"` and
   `description="L1 invoke failed: LLM subprocess timed out after Ns"`.
   BUT: the CONTEXT decision LOCKS "check the typed flag, NOT string-matching."
   This approach violates D-1.

2. **Typed flag on StateFinding (CONTEXT-compliant):** Add a
   `is_timeout: bool = False` field to the INFRA `StateFinding` created in
   `_provider()`. The `except LLMInvokeError as exc` block at
   `factories.py:295` has access to `exc.is_timeout` and can set
   `finding.is_timeout = True` on the StateFinding it creates. Then
   `_run_l1_phase()` checks `finding.is_timeout` on INFRA findings.

   This requires adding `is_timeout` to `StateFinding` (state.py:39).
   StateFinding already has optional fields (`error`, `anchor`,
   `evidence_files`). Adding one more boolean with `default=False` is
   additive and does not bump SCHEMA_VERSION (per the existing "additive
   only" convention at state.py:63).

   **Alternative:** Do NOT add to StateFinding. Instead, keep a separate
   mechanism: `_provider()` could return a 5th element (timeout_count) in
   its tuple, but that changes the L1Provider type alias (machine.py:59)
   and every caller. Heavier than the StateFinding field.

**Recommendation:** Add `is_timeout: bool = False` to `StateFinding`. It is
the least invasive path that honors the CONTEXT lock against string-matching.
The field is only meaningful for `source="INFRA"` findings; all other findings
default to `False` and the field is ignored. [VERIFIED: code read of state.py,
factories.py, machine.py at af378f9]

### D-1: Counter Lifecycle (grounded)

```
StateMachine.__post_init__():
    self._consecutive_l1_timeouts = 0  # in-memory, per-run

_run_l1_phase():
    findings = l1_provider()  # returns list[StateFinding]
    
    # Check for timeout INFRA findings
    has_timeout = any(
        f.source == "INFRA" and f.is_timeout
        for f in findings[0]  # findings is a tuple (candidates, excerpts, ...)
    )
    has_success = any(
        f.source != "INFRA"
        for f in findings[0]
    ) or (len(findings[0]) == 0 and diff_text is not empty)
    
    if has_timeout:
        self._consecutive_l1_timeouts += 1
    else:
        self._consecutive_l1_timeouts = 0  # any success resets
    
    if self._consecutive_l1_timeouts >= 5:
        ABORT with EXIT_TIMEOUT = 6
```

**Abort mechanism:** The abort must bypass the normal verdict path. Two options:

1. **Raise a dedicated exception** (e.g. `TimeoutAbort`) from `_run_l1_phase()`,
   caught in `_run_local()` / `_run_ci()`, which sets verdict and returns.
   This is clean but adds a new exception class.

2. **Return early from `_run_local()`** by checking the counter after
   `_execute_round()` returns. `_execute_round()` calls `_run_l1_phase()`
   internally. The counter check goes right after `_execute_round()` in the
   `_run_local()` for-loop (machine.py:466). This mirrors the existing
   `mutant_survivors` check pattern (machine.py:469-487).

**Recommendation:** Approach 2 (return early from `_run_local`). The existing
`consecutive_survivor_rounds` check (machine.py:469-487) is an exact structural
precedent: check a counter after `_execute_round()`, set verdict to FAIL, persist,
return. The breaker uses the same pattern but returns a distinct exit code.
[VERIFIED: machine.py:469-487 at af378f9]

**Exit code mapping:** `EXIT_TIMEOUT = 6` is added to `exit_codes.py`.
`verdict_to_exit()` maps `Verdict.FAIL` to `EXIT_FAIL` (1). The breaker
abort is NOT a normal FAIL verdict -- it needs its own exit path. Two options:

1. Add `Verdict.TIMEOUT` to the Verdict enum (state.py:29). CONTEXT says
   "Verdict enum does NOT gain a new member." This is RULED OUT by the lock.

2. Raise a custom exception (e.g. `TimeoutBreaker`) from `_run_local()` that
   is caught in `cli.py:987` (the `_run()` caller). `cli.py` catches it and
   returns `EXIT_TIMEOUT` directly, bypassing `verdict_to_exit()`. This
   parallels how `ForgeLockBusy` is caught at `cli.py:991-993` to return
   `EXIT_BUSY`. [VERIFIED: cli.py:991-993 at af378f9]

**Recommendation:** Custom exception approach. Define `class TimeoutBreaker(Exception)`
in machine.py (or a shared module). `_run_local()` raises it when the breaker trips.
`cli.py` catches it and returns `EXIT_TIMEOUT`. This keeps the Verdict enum
unchanged per the CONTEXT lock. [VERIFIED: the ForgeLockBusy precedent at cli.py:991]

### D-4: Path Normalization (the hard part)

Three path formats coexist:

| Source | Format | Example |
|--------|--------|---------|
| Diff headers | `+++ b/` prefix | `+++ b/src/foo.py` -> `src/foo.py` |
| Code excerpts | Plain relative | `src/foo.py` |
| Cross-repo diff | Absolute (D-23) | `/home/user/repo-b/src/foo.py` |

`parse_diff_files()` already strips the `b/` prefix (verify.py:43-44:
`line[6:]`). So for single-repo, diff files and excerpt files should match
directly on plain relative paths.

For cross-repo: the joint diff assembled by `build_cross_repo_context()`
(cross_repo.py:57-121) embeds raw per-repo diffs. Each per-repo diff uses
standard git diff format (`+++ b/path`), NOT absolute paths. The "absolute
paths" mentioned in D-23 refer to how the reviewer model may cite files in
its excerpts when given a cross-repo context -- the model sees the repo label
and may prefix paths with the repo label or an absolute path.

**Normalization strategy:**
- Extract basename from diff files: strip `b/` prefix (already done by
  `parse_diff_files()`).
- Extract basename from excerpt files: strip any leading `/` or repo-label
  prefix, then compare on the suffix (relative path portion).
- Match on `os.path.basename` + parent segments as a fallback if exact match
  fails.
- A simpler approach: normalize both sides to the file's relative path within
  its repo. For single-repo this is identity. For cross-repo, strip any
  absolute prefix up to and including the repo root.

**Test this normalization** with three shapes: `src/foo.py` (plain),
`b/src/foo.py` (diff prefix -- should never appear after parse_diff_files),
`/absolute/repo/src/foo.py` (cross-repo excerpt). The guard must not
over-fire (flag every pass as incomplete) or under-fire (never match).
[VERIFIED: verify.py:43-44 strips "b/" prefix; cross_repo.py:108-109
uses raw git diff format]

### Anti-Patterns to Avoid

- **String-matching for timeout detection.** CONTEXT locks a typed flag.
  Matching on `"timed out"` in the description is fragile and violates the
  lock.
- **Modifying the Verdict enum.** CONTEXT locks "Verdict enum does NOT gain
  a new member." The breaker abort must use a custom exception path.
- **Over-firing the coverage guard.** If path normalization is wrong, EVERY
  clean pass looks incomplete, churning cycles forever. The guard must have
  a negative test proving it does NOT fire when coverage is complete.
- **Touching lock.py.** Bug 4 is explicitly out of scope. The lock logic
  is correct (CONTEXT D-3).

## Common Pitfalls

### Pitfall 1: Breaker trips on non-timeout INFRA errors

**What goes wrong:** JSON parse failures or schema validation errors also
create INFRA findings. If the breaker counts ALL INFRA findings, a backend
that returns invalid JSON (but responds quickly) would incorrectly trip the
breaker.
**Why it happens:** Both timeout and non-timeout errors create INFRA findings
with the same `source="INFRA"`.
**How to avoid:** The `is_timeout` flag on `StateFinding` discriminates.
Only findings with `is_timeout=True` increment the counter.
**Warning signs:** Test with a backend that returns invalid JSON 5+ times --
breaker must NOT trip.

### Pitfall 2: Coverage guard path mismatch

**What goes wrong:** Diff files extracted via `parse_diff_files()` use plain
relative paths (`src/foo.py`). Excerpt files from the LLM may use a
different format (absolute, or with repo label prefix). The set intersection
is empty, so every pass looks incomplete.
**Why it happens:** The LLM is free to format paths however it wants in
code_excerpts. The prompt instructs `"file": "..."` but does not mandate
the format.
**How to avoid:** Normalize both sides. Match on the suffix: if a diff file
`src/foo.py` is a suffix of any excerpt file, it is covered.
**Warning signs:** Every single L1 clean pass gets an `incomplete-coverage`
INFRA finding, resetting cycles forever.

### Pitfall 3: Breaker fires in CI mode

**What goes wrong:** CI mode runs one round only (`_run_ci`, machine.py:230).
The breaker counter cannot reach 5 in one round (3 L1 passes max per round).
**Why it happens:** Each round runs 3 L1 passes (qodo/expert/adversarial).
Even if all 3 time out, that is only 3 increments.
**How to avoid:** The breaker is meaningful in LOCAL mode (multi-round loop).
In CI mode with 3 timeouts, the round completes with 3 INFRA findings and
FAIL verdict -- the breaker is not needed. Consider: should the breaker
check run in CI mode at all? Simplest answer: yes, it runs but cannot trip
(counter never reaches 5 in one round). This is correct behavior.
**Warning signs:** None -- this is a non-issue if understood.

### Pitfall 4: Cross-plan shared references drift

**What goes wrong:** D-1 and D-4 share `LLMInvokeError.is_timeout` and
`StateFinding.is_timeout`. If plans are split, plan A defines the flag and
plan B consumes it. If plan A's naming changes during review, plan B's
reference is stale.
**How to avoid:** Cross-plan consistency check (per project CLAUDE.md rule):
grep every plan doc for each shared ref before finalizing.
**Warning signs:** Plan B references `is_timeout` but plan A renamed it to
`timeout_flag`.

### Pitfall 5: EXIT_TIMEOUT conflicts with existing codes

**What goes wrong:** A new exit code 6 could conflict with a future
addition if not properly documented.
**Why it happens:** Exit codes are defined ad-hoc in exit_codes.py.
**How to avoid:** Add a completeness guard test (exit_codes already has
EXIT_PASS=0 through EXIT_DELEGATED=5; EXIT_TIMEOUT=6 is the natural next).
Check that the existing `test_exit_codes.py` tests cover the new constant.
**Warning signs:** Two constants with the same value.

### D-1: Breaker check in machine.py (after _execute_round)

```python
# machine.py _run_local(), after _execute_round() call (parallel to
# the consecutive_survivor_rounds check at lines 469-487)

# Check timeout circuit breaker
timeout_findings = [
    f for f in self._state.findings
    if f.source == "INFRA" and getattr(f, "is_timeout", False)
]
if timeout_findings:
    self._consecutive_l1_timeouts += len(timeout_findings)
else:
    self._consecutive_l1_timeouts = 0

if self._consecutive_l1_timeouts >= 5:
    self._state.verdict = Verdict.FAIL
    self._state.converged = False
    self._state.infra_errors.append(
        "timeout circuit breaker: %d consecutive L1 timeouts"
        % self._consecutive_l1_timeouts
    )
    self._persist_state()
    raise TimeoutBreaker(
        "backend produced %d consecutive timeouts; "
        "review cannot converge" % self._consecutive_l1_timeouts
    )
```

**IMPORTANT NOTE on counter semantics:** The CONTEXT says "increment on L1
infra-timeout, reset to 0 on any L1 success." Each round runs 3 L1 passes.
The counter must track across rounds (accumulating), not reset per-round.
A round with 2 timeouts and 1 success resets the counter to 0 (the success
clears it). A round with 3 timeouts increments by 3. After 2 rounds of all-
timeout (6 total), the breaker trips at the end of round 2.

The findings list is rebuilt each round (`_merge_findings` in `_execute_round`).
The counter must be updated BEFORE the findings are cleared, or use a different
mechanism. The `_run_l1_phase()` method is actually the better place: it has
direct access to the per-round L1 findings before merge. The counter update
can happen at the end of `_run_l1_phase()` and the breaker check at the top
of `_run_local()` after `_execute_round()`.

### D-4 Option B: Coverage guard in _provider()

```python

    from .verify import parse_diff_files

    norm_excerpts = {_normalize(f) for f in excerpt_files}

            id="l1-%s-incomplete-coverage" % pass_name,
            fingerprint="incomplete-coverage-%s" % pass_name,
            source="INFRA",
            disposition=Disposition.CONFIRMED,
            file="<coverage-guard>",
            line_range=[0, 0],
            description=(
                "L1 coverage guard: %d file(s) uncovered: %s"
                % (len(uncovered), ", ".join(sorted(uncovered)[:3]))
            ),
        ))
        continue  # do NOT count this as a clean pass
```

## Open Questions (RESOLVED)

1. **Counter granularity: per-pass or per-round?**
   - What we know: Each round has 3 L1 passes (qodo/expert/adversarial).
     CONTEXT says "consecutive L1 infra-timeouts" -- this means per-pass,
     not per-round.
   - What's unclear: If pass 1 times out and pass 2 succeeds, does the
     counter reset? CONTEXT says "reset to 0 on any L1 success" -- yes.
   - Recommendation: Per-pass granularity. 3 passes per round, each
     independently increments or resets the counter. 5 consecutive timeout
     passes (not rounds) trips the breaker. This means ~2 fully-timed-out
     rounds trip it.

2. **StateFinding.is_timeout serialization**
   - What we know: StateFinding is serialized to state.json via `asdict()`.
     Adding `is_timeout: bool = False` adds it to the JSON.
   - What's unclear: Does `load_state()` handle the new field? It uses
     `_finding_from_dict()` which constructs from explicit kwargs.
   - Recommendation: Add `is_timeout=d.get("is_timeout", False)` to
     `_finding_from_dict()`. Backward-compatible: old state.json without
     the field gets `False`.

3. **Coverage guard placement: per-pass or aggregate?**
   - What we know: `_provider()` loops over 3 passes. The guard could run
     per-pass or once after all passes.
   - What's unclear: Should a single pass that covers all files count as
     sufficient, even if other passes have gaps?
   - Recommendation: Per-pass. If pass 1 returns findings==0 but covers
     only 1 of 2 files, that pass is incomplete regardless of what other
     passes find. The guard fires per-pass to catch truncation early.

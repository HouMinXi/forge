## Convergent Findings (2+ models agree)

### CF-1: Counter placement is architecturally wrong [Plan 01] -- MM H1 + GM critical

**Models:** MiniMax (H1 counter semantics contradiction), Gemini (3-bug architectural analysis)

The plan puts the breaker counter in `machine.py`, reading `self._state.findings` after
`_execute_round()` to count timeout findings. This has multiple bugs:

- **Clean pass (0 findings):** counter never resets (MM: "partial-timeout round should reset";
  GM: "zero findings fails the reset condition")
- **JSON-parse INFRA (is_timeout=False):** falsely resets counter (GM: "not a success, but
  matches 'NOT an INFRA-timeout'")
- **Two contradictory implementation blocks in plan prose** (MM H1: first block does `+=`,
  second "simpler correct" block checks for non-timeout findings -- they disagree on
  partial-timeout rounds)

**Gemini's alternative:** Move counter entirely into `factories.py` `_provider()` closure.
The closure knows pass-level success/failure directly (increment on `exc.is_timeout`,
reset on `validate_reviewer_json` success, unchanged on other errors). Eliminates the
fragile findings-array inspection.

**Decision (2026-06-20):** Option C -- dedicated `TimeoutCircuitBreaker` object.
The breaker is a first-class object with its own state, created by StateMachine,
injected into `build_l1_provider()`. The closure calls `breaker.record_timeout()` /
`breaker.record_success()` / `breaker.record_other_error()` per pass. `record_timeout()`
raises `TimeoutBreaker` when the threshold is reached. This avoids both the fragile
findings-array reverse-engineering (Option A) and the closure-as-concern-owner smell
(Option B). The breaker is independently unit-testable.

## Why this borrows the 25.x number (user asked to state the reason)

These are backend/timeout/docs robustness problems with ZERO relation to
cross-repo review (Phase 25's actual subject). By GSD semantics a decimal phase
should belong to its parent's topic, so strictly this should be an independent
phase (e.g. Phase 30). The user authorized borrowing 25.1 for the P0 item only,
with the reason recorded here:

**Bug 5 (no timeout circuit breaker) blocks ALL forge review on slow backends,
including cross-repo review itself.** Phase 25 spawns N concurrent StateMachines
(one per repo) -- it is MORE exposed to the non-convergence-on-timeout failure
than single-repo review. Fixing backend robustness is a sensible prerequisite
that lands before cross-repo ships. That is the justification for the 25.x slot.
Everything in 25.1 that is NOT P0 code is docs, batched here for one pass.

<scope_challenge>
## Scope Challenge (mandatory before design)

**(a) Does this need to exist?** Yes for Bug 5. On a slow backend (every
cross-Pacific CN backend: kimi/deepseek/mimo/glm) forge currently runs cycle
after cycle of timeouts, never converging -- the user's field run did 14 cycles,
0 clean. The real findings are produced but drowned in timeout noise. This is a
real, reproduced P0.

**(b) Three real consumers:**
1. The user's own CN-backend forge runs (mimo-pro/kimi/ds are all slow,
   cross-Pacific, chosen for price -- the whole reason to support `type: api/cli`
   non-Anthropic backends).
2. Cross-repo review (Phase 25): N concurrent StateMachines multiply timeout
   exposure; without the breaker, cross-repo cannot converge on a slow backend
   either.
3. Any forge user whose backend has a transient outage mid-review -- today that
   hangs; the breaker turns it into a clear failure.

**(c) Cost of "do nothing + document":** The user has a workaround (run inline
review with Opus, never a slow backend). But that abandons the entire CN-backend
value proposition (chosen to save cost). "Do nothing" = forge is unusable on the
cheap backends it advertises support for, and cross-repo inherits the defect.
Documenting "only use fast backends" is a capability retreat, not a fix.

**Deferred by scope-challenge:**
- **Bug 7 (`doctor` subcommand):** 1 known consumer (the user, once). A
  connectivity self-test is nice but its demand signal is a single field report.
  Cheaper: a troubleshooting section in docs (folded into the docs sweep) that
  lists each backend type's expected behavior and the one error each produces.
  Revisit `doctor` if a second independent request appears.
- **Bug 4 (lock changes):** the lock is correct; touching it would be a fix in
  search of a bug. The circuit breaker removes the stuck-process root cause.
</scope_challenge>

<decisions>
## Implementation Decisions

### D-1: Circuit breaker = fail-fast abort, NOT "timeout as finding"
The field report proposed (a) count timeout as a P0 finding that resets the
cycle + (b) auto-switch to a faster model. BOTH are rejected:
- "timeout as finding" violates forge's settled design that infra errors are NOT
  findings (machine.py:69 "ToolError -> infra_errors, NOT promoted to
  StateFinding"). Polluting finding semantics with infra noise is the wrong axis.
- forge must not silently switch the model the user configured.

**Decision:** Track CONSECUTIVE L1 infra-timeouts. When the count reaches a
threshold (default 5), ABORT the review with exit code 6 and a clear message:
"backend produced N consecutive timeouts (>=Ns each); the review cannot
converge. Reduce diff size, raise FORGE_LLM_TIMEOUT_S, or switch to a faster
(non-reasoning) backend." Better to fail loudly than run 14 cycles pretending
to make progress. The counter resets on any successful L1 invoke.

LOCKED (2026-06-20 discuss-phase):
- **Timeout flag**: `LLMInvokeError` gains `is_timeout: bool = False`. Both
  timeout raise sites (llm_invoke.py: _invoke_cli TimeoutExpired and
  _invoke_anthropic/openai TimeoutError) set `is_timeout=True`. The breaker
  checks this flag, NOT string-matching. JSON-parse or other infra errors
  leave `is_timeout=False` and do NOT increment the breaker counter.
- **Exit code**: `EXIT_TIMEOUT = 6` in exit_codes.py. Distinct from FAIL (1).
  Verdict enum does NOT gain a new member -- the breaker raises before a
  verdict is computed; exit_codes.py maps the abort directly to 6.
- **Threshold**: default 5 (changed from draft's 3). Cross-Pacific backends
  have occasional single-request timeouts that are transient, not pathological.
  5 consecutive timeouts is a strong signal. NOT configurable via env var in
  this phase (YAGNI); revisit if a user requests it.
- **Counter lifecycle**: in-memory per-run (NOT persisted). Init 0, increment
  on L1 infra-timeout (is_timeout=True), reset to 0 on any L1 success, trip
  at threshold.
- **Insertion point**: left to planner (machine.py L1 phase, around the
  `except` that appends to infra_errors).

### D-4: L1 truncation false-green guard (from Phase 25 MEDIUM-1)

Cross-repo review (Phase 25) amplifies a pre-existing single-repo bug: a
truncated L1 response can parse as valid JSON with findings==[] and >=1
code_excerpt, passing validate_reviewer_json (reviewer_json.py:69) as a
genuine clean pass. No coverage check verifies excerpts cover every changed
file. The gross failure modes are already closed (factories.py:295-327,
reviewer_json.py:69-73, machine.py:120-123); this is the narrow residual path.

Full spec: /tmp/draft_l1_truncation_guard_20260619_101428.txt (grounded
against live code by main session 2026-06-19).

**Option B (primary, backend-agnostic coverage backstop):**
  Location: factories.py _provider(), AFTER validate_reviewer_json, ONLY when
  findings==0. Derive changed files from diff_text; derive covered files from
  code_excerpts. Any changed file with zero covering excerpts -> CONFIRMED
  INFRA "l1-{pass}-incomplete-coverage". Covers ALL backends including the
  claude -p CLI path (no stop_reason available).
  Path normalization caveat: diff uses "a/x b/x", excerpts use plain paths,
  cross-repo uses ABSOLUTE paths (D-23). Must normalize before comparing.

**Option A (secondary, truncation signal):**
  Plumb stop_reason through LLMResult (llm_invoke.py:36-40). Per adapter:
  anthropic stop_reason=="max_tokens", openai finish_reason=="length", vertex
  finishReason=="MAX_TOKENS". CLI envelope has no such field -> None (gap
  covered by Option B). Truncated -> CONFIRMED INFRA "l1-{pass}-truncated".

**Implementation order:** Option B first (raises the floor for every backend).
Option A if time allows (precision layer for adapter-routed calls).

**Bug-injection test:** stub backend returns findings==[], one excerpt covering
only 1 of 2 changed files -> assert INFRA finding appears. Comment out guard ->
test must fail. Negative test: full coverage -> no INFRA finding.

### D-4 field evidence (2026-06-20)
mimo-pro backend with max_tokens=8192 truncated the L1 text block mid-response.
forge reported "unexpected response structure" (llm_invoke.py _invoke_anthropic
parse path). Root cause: the API returned a valid Anthropic-format response
(content array with text + thinking blocks) but the text block was cut short by
the token limit. Raising max_tokens to 16384 fixed the immediate symptom, but
the underlying vulnerability is exactly D-4's target: a truncated response that
parses as valid JSON with incomplete coverage can silently produce a false-green
verdict. This is a real-world instance, not a hypothetical.
</decisions>

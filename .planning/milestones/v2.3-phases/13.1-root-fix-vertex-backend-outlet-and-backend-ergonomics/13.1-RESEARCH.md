## Summary

This phase fixes two design debts and adds one new capability across two commit waves. The research covers four domains: (1) the fail-fast default for zero-config execution, a straightforward guard in outlet_resolver.py; (2) Vertex AI Claude API wire protocol, verified from both Anthropic and GCP official docs scraped 2026-06-05; (3) the google-auth library for service account credential management, with a critical correction to the prior research about its dependency chain; and (4) CLI patterns for the `init` subcommand and deprecation aliases.

The most critical finding is that **Vertex AI Express Mode (API key auth) does NOT support Claude models**. The rawPredict endpoint required by Anthropic models only accepts OAuth2 bearer tokens via service account credentials or ADC. This is confirmed by Tailscale's Aperture docs (validated 2026-05-29) which explicitly state: "The Vertex AI raw predict endpoint required by Anthropic models does not support API key authentication." [VERIFIED: tailscale.com/docs/aperture/how-to/use-vertex-ai-express, scraped 2026-06-05]

A critical correction from prior research: **google-auth does NOT transitively depend on `requests`**. Its core dependencies are `cachetools`, `pyasn1-modules`, and `rsa` only. The `requests` library is declared only under `extra == "requests"`. However, `google.auth.transport._http_client.Request` provides a stdlib-only transport (using `http.client`) that IS a valid subclass of `google.auth.transport.Request` and can be used for `credentials.refresh()`. This means forge could theoretically refresh OAuth tokens without adding `requests` as a dependency. The tradeoff: `_http_client` is a private/internal API (underscore-prefixed). The safer alternative is to declare `requests>=2.20.0` in the `[vertex]` extra alongside `google-auth`.

**Primary recommendation:** Implement Wave 1 as pure guard logic (no new dependencies). Implement Wave 2's `_invoke_vertex` using `google.oauth2.service_account.Credentials` for token acquisition and `google.auth.transport.requests.Request()` for refresh, declaring both `google-auth>=2.35.0` and `requests>=2.20.0` in the `[vertex]` pyproject.toml extra.

### Pattern 1: Vertex AI rawPredict Wire Protocol

**What:** Vertex AI Claude uses `rawPredict` endpoints with Anthropic Messages API body format, but with critical differences from direct Anthropic API.
**When to use:** Any `format: vertex` backend in gate.yaml.

**Endpoint URL patterns:** [VERIFIED: scraped both docs 2026-06-05]

Global endpoint (recommended, no pricing premium):
[CITED: platform.claude.com/docs/en/build-with-claude/claude-on-vertex-ai]
[CITED: docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/claude/use-claude]
```
POST https://aiplatform.googleapis.com/v1/projects/{PROJECT_ID}/locations/global/publishers/anthropic/models/{MODEL}:rawPredict
```

Regional endpoint (10% premium):
```
POST https://{REGION}-aiplatform.googleapis.com/v1/projects/{PROJECT_ID}/locations/{REGION}/publishers/anthropic/models/{MODEL}:rawPredict
```

Multi-region endpoint (us/eu, 10% premium):
```
POST https://aiplatform.{MULTI_REGION}.rep.googleapis.com/v1/projects/{PROJECT_ID}/locations/{MULTI_REGION}/publishers/anthropic/models/{MODEL}:rawPredict
```

**Request body (from GCP use-claude curl example):**
[CITED: docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/claude/use-claude]
```json
{
  "anthropic_version": "vertex-2023-10-16",
  "messages": [{"role": "user", "content": "..."}],
  "max_tokens": 16384
}
```

**Key differences from `_invoke_anthropic` (4 total):**
1. `model` is NOT in the body -- it is in the URL path [VERIFIED: Anthropic docs + GCP docs both confirm]
2. `anthropic_version` is `"vertex-2023-10-16"` (NOT `"2023-06-01"`) and goes in the **body** (NOT the `anthropic-version` header) [VERIFIED: Anthropic docs state this explicitly]
3. Auth header: `Authorization: Bearer {oauth_token}` (NOT `x-api-key`) [VERIFIED: GCP curl example uses `gcloud auth print-access-token`]
4. No `x-api-key` header at all

**Response format:** Identical to Anthropic Messages API [VERIFIED: GCP use-claude response example]:
```json
{
  "id": "msg_...",
  "type": "message",
  "role": "assistant",
  "content": [{"type": "text", "text": "..."}],
  "usage": {"input_tokens": 11, "output_tokens": 11}
}
```

Note: `rawPredict` (non-streaming) vs `streamRawPredict` (streaming). Forge uses non-streaming since it waits for full response.

### Pattern 2: google-auth Service Account Token Flow

**What:** Load SA credentials from JSON key file, generate scoped OAuth2 access token, auto-refresh on expiry.
**When to use:** `_invoke_vertex` needs a bearer token for each request.

**Dependency chain (CORRECTED from prior research):**
[VERIFIED: `pip show google-auth` + `importlib.metadata.requires('google-auth')` on local install 2026-06-05]

- google-auth core deps: `cachetools`, `pyasn1-modules`, `rsa` ONLY
- `requests` is NOT a core dep -- it is under `extra == "requests"` and `extra == "aiohttp"`
- `google.auth.transport.requests.Request()` does `import requests` at module load time -- will ImportError if requests is not installed
- `google.auth.transport._http_client.Request()` uses stdlib `http.client` only -- IS a valid `transport.Request` subclass (verified via `issubclass()`) but is prefixed with underscore (private API)
- `google.auth.transport.urllib3.Request()` uses urllib3 -- also valid, but urllib3 is also not a core dep

**Recommendation:** Declare BOTH `google-auth>=2.35.0` AND `requests>=2.20.0` in the `[vertex]` pyproject.toml extra. This ensures `google.auth.transport.requests.Request()` works and uses a public, documented API path.

**Code pattern:** [CITED: google-auth.readthedocs.io/en/latest/user-guide.html]
```python
from google.oauth2 import service_account
import google.auth
import google.auth.transport.requests

# Option A: Explicit SA key file path (credentials_path in BackendConfig)
credentials = service_account.Credentials.from_service_account_file(
    credentials_path,
    scopes=['https://www.googleapis.com/auth/cloud-platform'],
)

# Option B: ADC fallback (GOOGLE_APPLICATION_CREDENTIALS env var)
credentials, _ = google.auth.default(
    scopes=['https://www.googleapis.com/auth/cloud-platform'],
)

# Refresh token (makes HTTP request to Google's token endpoint)
auth_request = google.auth.transport.requests.Request()
credentials.refresh(auth_request)

# Use token with urllib.request
headers = {"Authorization": "Bearer " + credentials.token}
```

**Token lifecycle:**
- `credentials.valid` -- True if token exists and not expired
- `credentials.expired` -- True if token has expired
- `credentials.refresh(request)` -- Obtains new token (idempotent if valid)
- Token TTL is typically 3600s (1 hour)
- For forge's use case (single review request), refresh once per invocation is sufficient

**ADC resolution order:** [CITED: google-auth.readthedocs.io/en/latest/user-guide.html]
1. `GOOGLE_APPLICATION_CREDENTIALS` env var (points to SA key JSON file)
2. `gcloud auth application-default login` credentials
3. GCE metadata server (when running on Google Cloud)

### Pattern 4: Endpoint URL Construction

**What:** Build the correct Vertex endpoint URL based on the region type.
**When to use:** `_invoke_vertex` URL construction.

```python
def _build_vertex_url(project_id: str, region: str, model: str) -> str:
    """Build Vertex AI rawPredict endpoint URL.

    Handles global, regional, and multi-region endpoints.
    Source: Verified from Anthropic docs + GCP use-claude docs 2026-06-05.
    """
    if region == "global":
        base = "https://aiplatform.googleapis.com"
    elif region in ("us", "eu"):
        # Multi-region
        base = "https://aiplatform.%s.rep.googleapis.com" % region
    else:
        # Regional (e.g., us-east5, europe-west1)
        base = "https://%s-aiplatform.googleapis.com" % region
    return (
        "%s/v1/projects/%s/locations/%s"
        "/publishers/anthropic/models/%s:rawPredict"
        % (base, project_id, region, model)
    )
```

### Anti-Patterns to Avoid

- **Hand-writing Vertex endpoint URLs from memory:** The endpoint shape changed when GCP rebranded to "Gemini Enterprise Agent Platform". Always derive from D-13 verified docs. The prior docs URL (`cloud.google.com/vertex-ai/generative-ai/docs/partner-models/use-claude`) now redirects to `docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/claude/use-claude`.
- **Storing OAuth tokens in gate.yaml:** Tokens are ephemeral (1hr TTL). Only the SA key file path goes in config. Token is generated at invocation time.
- **Using anthropic-version header for Vertex:** Vertex requires `anthropic_version` in the request **body**, not as a header. Using the header silently fails.
- **Importing google-auth at module load time:** D-12 makes it optional. Import inside `_invoke_vertex` with try/except ImportError that raises a clear CliError message telling users to `pip install code-review-forge[vertex]`.
- **Assuming google-auth brings requests transitively:** It does NOT. The `[vertex]` extra must declare `requests>=2.20.0` explicitly alongside `google-auth>=2.35.0`.
- **Using `_http_client` private transport:** While it works (verified by `issubclass` check), it is underscore-prefixed internal API. Use the documented `google.auth.transport.requests.Request()` path instead.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| GCP OAuth2 token management | Custom JWT signing + token refresh | google-auth `service_account.Credentials` | JWT signing, token caching, expiry detection, refresh retry are all edge-case-heavy |
| YAML template generation | Complex Jinja2 template engine | Static string with `textwrap.dedent` | Template is fixed content, no variables beyond comments |
| Deprecation warning dispatch | Custom warning framework | `print(..., file=sys.stderr)` | Python's `warnings` module adds noise (stack trace, filter complexity). A single stderr line per CONTEXT.md spec is cleaner |
| Vertex rawPredict endpoint URL | Manual string concatenation | Named format with validation + multi-region dispatch | Region/project/model all need validation; three different base URL patterns (global/regional/multi-region) |

## Common Pitfalls

### Pitfall 1: anthropic_version Placement (Vertex vs Direct)
**What goes wrong:** Vertex requests silently fail or return 400 when `anthropic_version` is sent as a header instead of in the body.
**Why it happens:** Direct Anthropic API uses `anthropic-version` header. Vertex moved it to body field `anthropic_version` (underscore, not hyphen).
**How to avoid:** `_invoke_vertex` must construct the body with `"anthropic_version": "vertex-2023-10-16"` and NOT set any anthropic-version header. The only headers are `Authorization: Bearer {token}` and `Content-Type: application/json`.
**Warning signs:** HTTP 400 "invalid request" from Vertex.

### Pitfall 2: Model ID in Body vs URL
**What goes wrong:** Vertex returns 404 or ignores the model field if `model` is in the request body.
**Why it happens:** Vertex requires model in the URL path (`.../models/{MODEL}:rawPredict`), not in the body. Direct Anthropic API puts model in the body.
**How to avoid:** `_invoke_vertex` must NOT include `"model"` in the JSON body. It goes in the URL only.
**Warning signs:** 404 "model not found" or wrong model used.

### Pitfall 3: google-auth Import Error at Runtime
**What goes wrong:** User configures `format: vertex` in gate.yaml but hasn't installed `code-review-forge[vertex]`. Import fails at review time.
**Why it happens:** google-auth is optional (D-12).
**How to avoid:** Catch ImportError in `_invoke_vertex` (or at `_invoke_api` dispatch time) and raise `LLMInvokeError` with explicit install instructions: `pip install code-review-forge[vertex]`.
**Warning signs:** ImportError traceback instead of user-friendly message.

### Pitfall 4: google-auth Token Refresh Requires `requests` Library
**What goes wrong:** `google.auth.transport.requests.Request()` fails with ImportError because `requests` is not installed.
**Why it happens:** google-auth's core deps do NOT include `requests`. The `google.auth.transport.requests` module does `import requests` at the top level. If `requests` is not present, the import fails.
**How to avoid:** The `[vertex]` extra in pyproject.toml MUST declare both `google-auth>=2.35.0` AND `requests>=2.20.0`. The ImportError catch in `_invoke_vertex` should cover both packages with a single message pointing to `pip install code-review-forge[vertex]`.
**Warning signs:** ImportError on `google.auth.transport.requests` even when google-auth is installed.

### Pitfall 5: Zero-Config Guard Must Check BEFORE Reachability Probe
**What goes wrong:** If the fail-fast check happens after `resolve_outlet` starts probing, the 120s timeout still occurs.
**Why it happens:** `resolve_outlet` calls `reachability_fn()` at step 3 (line 175). The guard in D-01 must fire before this.
**How to avoid:** The check belongs in `resolve_outlet` itself or in `_run()` before calling `resolve_outlet`. When `configs==[]` and no explicit outlet/env override, raise CliError immediately instead of falling through to `reachability_fn()`.
**Warning signs:** Timeout still occurs despite guard code existing.

### Pitfall 6: Outlet Rename Breaks --outlet argparse choices
**What goes wrong:** `--outlet choices=["cli", ...]` in argparse will reject "subprocess" if not updated.
**Why it happens:** argparse validates choices before the handler code runs.
**How to avoid:** Update `--outlet choices` to `["subprocess", "cli", "inline", "subagent"]` -- keeping "cli" in the choices list so argparse accepts it, then handle the deprecation warning in `_parse_outlet_string`. Alternatively, remove `choices=` from argparse and let `_parse_outlet_string` handle all validation including deprecation.
**Warning signs:** argparse rejects the new value with "invalid choice: 'subprocess'".

### Pitfall 7: Vertex format-aware Validation in _parse_backend_entry
**What goes wrong:** The existing `_parse_backend_entry` requires `base_url` and `api_key_env` for ALL api-type backends. Vertex needs neither.
**Why it happens:** The validation was written when only openai and anthropic formats existed, both of which need base_url + api_key_env.
**How to avoid:** Add a format-aware branch: for `format: vertex`, skip `base_url` and `api_key_env` validation. Instead require `project_id` (and optionally `region`, defaulting to "global"). Keep existing validation for openai/anthropic formats unchanged.
**Warning signs:** CliError "missing required field 'base_url'" when configuring a vertex backend.

### Pitfall 8: Multi-Region Endpoint URL Pattern Differs
**What goes wrong:** Using `us-aiplatform.googleapis.com` instead of `aiplatform.us.rep.googleapis.com` for multi-region.
**Why it happens:** Multi-region (us/eu) uses a different base URL pattern than regional endpoints. The Anthropic docs show this via SDK region values "us" and "eu".
**How to avoid:** The URL builder must have three branches: global, multi-region (us/eu), and regional. See Pattern 4 code example.
**Warning signs:** HTTP errors or routing failures when using region="us" or region="eu".

### Example 1: _invoke_vertex Implementation Skeleton

```python
# Source: Vertex AI Claude docs (verified via Firecrawl scrape 2026-06-05)
# + google-auth docs (verified via Firecrawl scrape 2026-06-05)

def _invoke_vertex(
    prompt: str,
    backend: BackendConfig,
    timeout_s: int,
) -> tuple[str, dict]:
    """Vertex AI rawPredict call. Returns (content_str, usage_dict)."""
    try:
        from google.oauth2 import service_account
        import google.auth
        import google.auth.transport.requests
    except ImportError as exc:
        raise LLMInvokeError(
            "Vertex AI format requires google-auth and requests. "
            "Install: pip install code-review-forge[vertex]"
        ) from exc

    # Resolve credentials: explicit path > ADC
    if backend.credentials_path:
        credentials = service_account.Credentials.from_service_account_file(
            backend.credentials_path,
            scopes=["https://www.googleapis.com/auth/cloud-platform"],
        )
    else:
        credentials, _ = google.auth.default(
            scopes=["https://www.googleapis.com/auth/cloud-platform"],
        )

    # Refresh token
    auth_request = google.auth.transport.requests.Request()
    credentials.refresh(auth_request)

    # Build endpoint URL (handles global/regional/multi-region)
    url = _build_vertex_url(
        backend.project_id, backend.region or "global", backend.model
    )

    # Build body -- NO model field, anthropic_version in body NOT header
```

## Open Questions (ALL RESOLVED)

1. **Vertex `api_key_env` field semantics for format=vertex**
   - **RESOLVED:** Vertex does not use API keys. `_parse_backend_entry` must add a format-aware branch: for vertex, skip `api_key_env` and `base_url` validation, require `project_id` instead.

2. **google-auth `requests` transitive dependency**
   - **RESOLVED:** requests is NOT a transitive dep. Verified via `pip show google-auth` (Requires: cryptography, pyasn1-modules) and `importlib.metadata.requires('google-auth')` (core: cachetools, pyasn1-modules, rsa; requests only under extra). The `[vertex]` extra must declare both packages.

3. **BackendConfig frozen dataclass extension**
   - **RESOLVED:** All BackendConfig construction uses keyword arguments (confirmed in `_parse_backend_entry`). New Optional fields with None defaults are backward-compatible.

4. **Vertex Express Mode API key support for Claude**
   - **RESOLVED:** Express Mode does NOT support Claude. Confirmed by Tailscale Aperture docs (2026-05-29): "The Vertex AI raw predict endpoint required by Anthropic models does not support API key authentication." Claude requires full OAuth2.

5. **Multi-region endpoint URL pattern**
   - **RESOLVED:** Multi-region (us/eu) uses `aiplatform.{region}.rep.googleapis.com`, distinct from regional `{region}-aiplatform.googleapis.com`. Anthropic docs SDK examples show region="us" and region="eu" as valid values.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| SA key file exposure in gate.yaml | Information Disclosure | `credentials_path` stores file path, not key content. Path is not logged. |
| Token in error messages | Information Disclosure | Never include `credentials.token` in error messages or logs |
| Untrusted gate.yaml credentials_path | Tampering | Pre-existing SEC-01 (untrusted gate.yaml) applies. No new surface added beyond existing api_key_env pattern. |
| Token refresh network call | Denial of Service | google-auth refresh can fail/timeout. Catch `google.auth.exceptions.RefreshError` with user-friendly message. |

## Phase Details

### Phase 5: Prerequisites
**Goal**: The foundational infrastructure exists for both outlets -- the configured review backend is verified reachable (backend-agnostic per BACKEND-01), projects auto-detect their toolchain, and the outlet selection logic is designed
**Depends on**: Phase 4 (v2.1 complete)
**Requirements**: CLI-03, CLI-04, CLI-05, BOTH-04, BACKEND-01 (Phase 5 = abstraction + config schema + resolution order + reachability probe only; API/CLI adapter implementations deferred to Phase 7 per D-30)
**Success Criteria** (what must be TRUE):
  1. User runs `code-forge review` in a Python project with no tools.yaml and gets L0 linting from auto-detected ruff/pylint/flake8 without manual config
  2. First-run auto-init generates a minimal tools.yaml from detected toolchain, and user sees what was detected and what was missing
  3. Running the reachability probe against the configured backend returns OK within 20 seconds when reachable (for the default `claude -p` backend this is `claude auth status`); with unreachable/missing auth it returns a clear error naming the missing piece
  4. SKILL.md outlet selection: explicit env-var override wins; with no override, selection uses ONLY the objective configured-backend-reachability signal, and the fail-safe default is Outlet A (CLI). It does NOT auto-detect model capability -- a model cannot reliably self-assess trustworthiness (the reason Reviewer Canary exists), and self-rating would route weak models into inline self-drive
**Plans**: 4 plans
Plans:
- [x] 05-01-PLAN.md -- Toolchain auto-detection (detect.py + tests)
- [x] 05-02-PLAN.md -- Backend abstraction + config schema + backend-agnostic reachability probe (backend.py + tests)
- [x] 05-03-PLAN.md -- Outlet resolver over backend reachability (outlet_resolver.py + tests)
- [x] 05-04-PLAN.md -- CLI integration (detect + resolve-outlet subcommands + review auto-detect)

### Phase 6: Outlet B Inline Merge
**Goal**: Trusted strong models (e.g. terminal Opus) can run the full 3-pass review inline without sub-skill Invoke calls, eliminating the hang bug
**Depends on**: Phase 5 (outlet selection logic determines routing)
**Requirements**: INL-01, INL-02, INL-03, INL-04, INL-05, BOTH-01
**Success Criteria** (what must be TRUE):
  1. User invokes `/code-forge` from terminal Opus and the review runs all 3 passes inline without hanging (no "Launching skill: X" blocks)
  2. Findings from all 3 passes use unified P0-P3 severity instead of per-pass vocabularies (R/Y/G, Critical..Nit, P0-P3)
  3. User can run a single pass standalone via `step N` argument (e.g. adversarial-only)
  4. Each pass prompt includes "systematically cover the whole diff risk surface" instruction

### Phase 7: Outlet A CLI Dispatcher
**Goal**: Untrusted/cheap editor models dispatch review to `code-forge review` CLI subprocess, with mechanical enforcement and fail-closed error handling
**Depends on**: Phase 5 (auth probe + auto-detect), Phase 6 (SKILL.md structure established)
**Requirements**: CLI-01, CLI-02, CLI-06, CLI-09, BOTH-03, BACKEND-01 (Phase 7 = the BACKEND-01 adapter implementations: HTTP clients for both API formats + cli wrappers, per D-30)
**Success Criteria** (what must be TRUE):
  1. User invokes `/code-forge` from an editor (e.g. VS Code Claude extension) and the review runs via `code-forge review` subprocess, not inline self-drive
  2. If `code-forge review` fails for any reason (missing binary, auth failure, timeout), SKILL.md reports the error and STOPS -- never silently degrades to self-drive
  3. Each review pass runs as a fresh backend invocation (a subprocess for `cli` backends, an HTTP request for `api` backends) with no context leakage between passes
  4. After CLI exits, SKILL.md reads `.code-forge/state.json` for findings display instead of parsing stderr
  5. `code-forge review` verifies it is running inside a linked worktree (not main tree) before starting
**Plans**: 3 plans
Plans:
- [x] 07-01-PLAN.md -- SKILL.md Outlet A dispatch (Bash tool invocation + state.json reader)
- [x] 07-02-PLAN.md -- Backend adapter implementations (API HTTP clients + CLI wrappers)
- [x] 07-03-PLAN.md -- Worktree validation + SKILL.md error display

### Phase 8: Hardening
**Goal**: Outlet A is production-ready with subprocess lifecycle safety, cost visibility, and documented configuration for all editor environments
**Depends on**: Phase 7 (Outlet A operational)
**Requirements**: CLI-07, CLI-08, BOTH-02
**Success Criteria** (what must be TRUE):
  1. When user cancels a review mid-run (Ctrl-C, close editor tab), all spawned review subprocesses (`cli` backends, e.g. `claude -p`) are killed within 10 seconds -- no orphan accumulation
  2. After review completes, user sees a cost summary showing total token usage and estimated cost from the pipeline run
  3. Backend configuration (`FORGE_BACKEND`, per-backend `model` + `api_key_env`) and auth are documented with setup guides for VS Code, Cursor, and terminal workflows

### Phase 10: detect.py Hardening
**Goal**: code-forge detect generates the L0 toolchain safely for multi-language projects -- it neither clobbers user-added non-Python tool entries nor leaves a shared-mutable alias. Auto-detect stays idempotent and multi-lang-safe
**Depends on**: Phase 5 (detect.py introduced)
**Requirements**: DET-01
**Success Criteria** (what must be TRUE):
  1. `code-forge detect --force` preserves a user-added non-Python tools.yaml entry (e.g. shellcheck) instead of clobbing it
  2. A generated tools.yaml entry does not share a mutable file_patterns list with the module constant -- deep copy, no aliasing
  3. detect knows at least one non-Python tool (shell/shellcheck) as a multi-language starting point

### Phase 11: Subagent-Dispatch Review Outlet
**Goal**: forge has a review outlet that needs neither an external `claude -p` subprocess (cold-start routinely >120s) nor an API key. The code-forge skill tells the session model to spawn one fresh subagent per review pass. Fresh context per pass = the same anti-fabrication the `claude -p` fresh subprocess gave, without cold-start and without API spend. Distinct from Outlet B inline (Phase 6), which runs all 3 passes in ONE shared context
**Depends on**: Phase 7 (Outlet A CLI dispatcher), Phase 6 (SKILL.md structure)
**Requirements**: BACKEND-02
**Success Criteria** (what must be TRUE):
  1. A third outlet/backend type (subagent) exists: the code-forge skill directs the session model to spawn a fresh subagent per review pass -- not a `claude -p` subprocess, not an API call
  2. Viability gate checked first: confirm the Agent/Task tool does not hang the way sub-Skill Invoke did (feedback_subagent_hangs) before building it
  3. --model-pin no-pin contract bug fixed: omit the --model flag when effective_model is empty
  4. Fail-closed error handling, consistent with Outlet A
**Plans**: TBD

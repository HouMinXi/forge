## WHY THIS EXISTS

The ledger's whole purpose is to record which findings were real and
which the review MISSED. An ESCAPED row is the only record forge will
ever have of a bug its own pipeline failed to catch, and it is not
reconstructible later -- the review that missed it produced no finding,
no fingerprint, no anchor. If it is not captured at mark time, it is
gone.

Today a real ESCAPED row was written end-to-end for the first time. This
is what came back out (`code-forge ledger list`, verbatim):

    ts                    fingerprint         terminal_state  file:line
    2026-07-30T12:53:52Z  exp1-escaped-0001   ESCAPED         :0

`file:line` is empty. The row says a bug escaped and says nothing about
where. That is the defect.

## GROUND TRUTH -- measured 2026-07-30, re-verify anything you rely on

  U1. `ledger mark` accepts two positionals and four options
      (cli.py ~690-716): fingerprint, terminal_state, --evidence,
      --new, --base-sha, --head-sha. There is no way to pass a file,
      a line, or a claim.

  U2. The row is built with three hardcoded placeholders,
      cli.py:1315-1318:

        file="",
        line=0,
        axis_claim="manual",
        pass_provenance="manual",

  U3. ledger.py performs NO field validation. append_row writes
      whatever it is handed; there is no raise, no assert, no
      emptiness check anywhere in the module.

  U4. The codebase documents an invariant that this path violates.
      machine.py:1170, describing the AUTOMATIC writer:

        non-git runs (where SHAs are unavailable) yield 0 to satisfy
        the "no placeholder/empty values" invariant.

      So the automatic writer would rather write nothing than write a
      placeholder, while the manual writer writes three of them. Two
      writers, one documented invariant, opposite behaviour. Whether
      that is a second defect or an intended asymmetry is part of what
      you decide below.

## THE ITEM

Let `ledger mark` record where the escape happened: a file, a line, and
the claim (what the missed bug actually was).

DECIDE AND ARGUE, do not assume:

  (a) Required or optional? Making them required is the only way to
      guarantee no future row is placeholder-only, but it breaks the
      existing two-positional CLI contract and any script using it.
      Making them optional preserves compatibility and leaves the hole
      open when they are omitted. A third option exists -- required for
      ESCAPED/DUPLICATE (the `--new` states, where there is no prior
      run to inherit from) and optional elsewhere. Argue whichever you
      pick; I am not pinning it.

  (b) What does `axis_claim` mean for a manual row? For automatic rows
      it names the review axis that raised the finding. For an escape
      there was no axis -- that is the point. Decide whether the field
      carries the human's description of the missed bug, the axis that
      SHOULD have caught it, or something else, and say why. This
      choice determines whether the data is useful in a year.

  (c) U4's asymmetry: does your change bring the manual path into line
      with the documented invariant, or do you argue the asymmetry is
      correct and the docstring should say so? Either is acceptable
      with an argument. Silently leaving them contradictory is not.

Validation is yours to design, but a line number that is not a positive
integer, and a file path that escapes the repo, are the obvious ones.

## Product finding that shapes this phase

Two of the three requested credential paths ALREADY EXIST:
- Connected account (client's model): outlet "sampling" is a
  first-class outlet -- outlet_resolver.py:12 "Outlet D (MCP
  client's own model, no API key)", :51 mapping;
  factories.py:440 build_sampling_l1_provider;
  init_template.py:17 documents it. Zero keys, zero wrapper.
- Vertex (own cloud): format "vertex" authenticates via
  credentials_path service-account JSON + OAuth2
  (backend.py:94; llm_invoke.py:733 comment "not needed for
  vertex which uses OAuth2"). Zero env keys, zero gpg.
The third (api key + url, i.e. CN/openai-format backends) exists
EXCEPT key delivery is env-var-only (backend.py:88 api_key_env,
llm_invoke.py:739 os.environ.get at call time). Env-only is what
forced this machine's launch wrapper (~/.local/bin/
code-forge-mcp-pass: two `pass show` gpg calls before exec; no
TTY at MCP spawn => cold gpg agent = dead/hung wrapper = client
shows "failed"). The wrapper is machine-local and untracked; the
official setup_mcp.py:250 registration is already direct
`code-forge-mcp`.

So: do NOT build a new credential system. Close two real product
gaps, flip onboarding to the robust paths that already exist,
and the wrapper retires.

## Flatpak-spawn fragility (measured 2026-07-04, why sampling matters most)

Independent of the gpg wrapper, the Flatpak VS Code surface has a
SECOND spawn failure that forge cannot fix from its own code:
- flatpak-spawn --host inherits the caller's cwd. VS Code exposes
  the open workspace as a DOCUMENT-PORTAL path
  (/run/flatpak/doc/<hash>/<folder>) that exists ONLY inside the
  sandbox. flatpak-spawn --host then tries to chdir to it ON THE
  HOST, which fails: "Failed to change to directory
  /run/flatpak/doc/.../ping-ws (No such file or directory)",
  server exits code 1, zero output. Verified live: a minimal MCP
  server failed exactly this way; adding --directory=<host path>
  (e.g. --directory=/tmp) fixed it -- full MCP initialize
  handshake then succeeded through flatpak-spawn --host.
- Implication for forge's own VS Code config: the launch line
  needs --directory=<a real host path>. For forge specifically,
  since it walks up from cwd to find .code-forge/gate.yaml,
  --directory=<host project root> serves double duty (valid host
  cwd + the project to review). A portal cwd breaks BOTH the
  chdir and the walk-up.
- This is why the sampling outlet is the strongest onramp for
  Flatpak IDE users: it borrows the client's own model over the
  existing stdio channel -- NO host subprocess spawn at all, so
  neither the gpg-wrapper nor the flatpak-spawn-cwd failure can
  occur. Vertex (credentials_path, still a host spawn) avoids gpg
  but NOT the cwd issue. Document the --directory requirement in
  the T3 onboarding matrix for any spawn-based Flatpak config.

## Tasks

T1 FORGE_PROJECT_DIR validation + fallback (mcp_server.py:106).
   If set but not an existing directory: log a WARNING naming the
   stale path, then fall through to the existing walk-up
   resolution instead of returning the dead path. Kills the
   pinned-rot class for every future session.

T2 api_key_path backend field (file-based key delivery).
   New optional field beside api_key_env, mirroring the
   credentials_path pattern: absolute/~ path to a file whose
   trimmed content is the key. Resolution order at call time:
   env var (if api_key_env set and non-empty) -> api_key_path ->
   CliError naming BOTH sources tried. Warn if the key file is
   group/world-readable (do not hard-refuse; containers and
   shared rigs have legitimate odd perms -- state this rationale
   in a comment).
   SECURITY (must be in your plan): api_key_path + endpoint are
   both config-controlled; a malicious PROJECT gate.yaml could
   read an arbitrary file and exfiltrate it as a bearer header to
   its own endpoint. This field must sit behind the existing
   trust gate EXACTLY like credentials_path already does. Verify
   untrusted-project behavior refuses api backends (existing
   mechanism) and add a regression test if none covers it.

T3 Onboarding flip (setup_mcp.py + README).
   - Credential matrix in setup-mcp output + README: (a) sampling
     outlet: zero-key, MCP-only; document the honest caveat that
     the reviewer is the SAME model family as the author, so
     independence is weaker -- fine as onramp, not the strongest
     review config; (b) vertex credentials_path; (c) api_key_path
     file for key+url backends; (d) plain env var stays supported.
   - Verify the printed `claude mcp add` line embeds env var
     NAMES/references only, never raw key values (backend.py:79
     posture). Fix if it interpolates secrets.
   - Presets currently detect backends via env presence
     (setup_mcp.py:97); extend detection to api_key_path
     existence so file-based users get the same one-command path.

T4 Wrapper disposition (docs only in this repo).
   README note: the pass/gpg wrapper pattern remains a valid
   opt-in for pass users but is no longer needed for GUI spawn
   once T2 lands; recommend direct `code-forge-mcp` registration.
   (Tracking the machine-local wrapper into the user's dotfiles
   repo is a user-side task, out of this repo's scope.)

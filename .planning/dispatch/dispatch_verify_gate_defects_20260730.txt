## ITEM A -- verify.py:271 hardcodes cycles 1 through 3

    expected = {(c, p) for c in range(1, 4) for p in range(1, 4)}
    if seen_keys != expected:
        return VerifyResult(False, "missing cycle/pass combinations", 1, cp)

The constraint is already documented against itself at verify.py:250-253:

    # Known design constraint: expects exactly cycles 1-3 x passes 1-3.
    # Reviews that take >3 total rounds write cycle 4+ receipts and fail
    # this check. Intended for post-convergence verification only (the
    # last 3 consecutive clean cycles produce the authoritative 9
    # receipts).

The comment states the intent: the last three clean cycles are what
matters. The code does not implement that -- it demands that the three
clean cycles be numbered 1, 2 and 3. A review that needed four rounds
has three clean cycles too; they are numbered 2, 3 and 4.

PINNED: verify the LAST three consecutive cycles present, whatever their
numbers, with all three passes each. Do not lower the count below 9
receipts and do not accept a set with a gap between the three cycles.

Decide and state which of these the check should treat as failure, and
why: (a) fewer than 3 cycles present, (b) 3 cycles present but not
consecutive, (c) more than 3 cycles present where the last 3 are
consecutive and complete. My reading is that (c) is the normal case for
any review that took more than three rounds, but the decision is yours
to argue -- if you believe (c) must stay a failure, say so with the
reason and stop there.

Do NOT add an env var or a flag to relax the check. A gate whose
strictness is caller-controlled is not a gate.

## ITEM B -- verify.py:358-369 rejects extra context

    if exc["file"] in hunk_map:
        overlaps = any(
            max(exc["start_line"], h["start"]) <= min(exc["end_line"], h["end"])
            for h in hunk_map[exc["file"]]
        )
        if not overlaps and exc["file"] not in exempt_files:
            return VerifyResult(False, "excerpt %s:%d-%d not in any diff hunk" ...)

One excerpt outside the hunks fails the whole attestation. Per U3 and U4
that happened with 8 of 9 excerpts anchored and full hunk coverage
satisfied.

The check exists to catch a fabricated excerpt -- a reviewer inventing
code it never read. An excerpt of real, unchanged, adjacent code is not
that. It is what a reviewer does when the change only makes sense next to
its neighbours. Note STEP C (verify.py:371-395) already compares excerpt
content against the diff post-image line by line, so fabrication inside
the hunks is caught there; an excerpt wholly outside the post-image
simply has no line to compare.

PINNED: an excerpt that lies outside every hunk must not by itself fail
the attestation, PROVIDED the hunk coverage requirement of STEP A is
satisfied. Fabrication detection must not weaken: an excerpt claiming
content that does not match the file it cites must still fail.

The obvious hole in the above, and the part I want you to close: if an
out-of-hunk excerpt is simply ignored, a reviewer can pad its receipt
with excerpts of code it never looked at and nothing checks them. STEP C
cannot help, because out-of-hunk lines are absent from the post-image.
Say how you close that. Verifying such an excerpt against the working
tree is one option and it has a TOCTOU problem the current design
deliberately avoids (see the comment at verify.py:372); if you take
that route, state why the exposure is acceptable, and if you reject it,
state what you do instead. An answer of "ignore them entirely, the
coverage floor makes padding pointless" is acceptable if you can show
the floor actually makes it pointless -- check 6 at verify.py:401 exists, read it before
relying on it.

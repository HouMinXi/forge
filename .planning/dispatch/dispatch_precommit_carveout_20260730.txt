## WHY THIS EXISTS

A change to src/code_forge/lock.py that rewrote nothing but the text of
an exception message -- zero control-flow change -- could not be
committed. Every route closed:

    git commit               pre-commit's attestation gate refused
    git commit --no-verify   a separate guard forbids bypassing hooks
    code-forge review        refuses to run in a main tree

That change is chore-class by forge's own rule. ~/CLAUDE.md, "Classify
the change first":

    Config / docs / chore / trivial text takes NO review -- this
    INCLUDES such a change living inside a .sh/.py/.go file: a
    comment, a help/error string, a constant, a version bump, a
    moved line.

The gate cannot see that category. This is not a request to weaken the
gate; it is a request to make the gate and the document stop
contradicting each other, in whichever direction survives argument.

## ITEM A -- the carve-out cannot express a chore change inside a code file

Decide, argue, and implement whichever of these survives:

  (a) Keep it filename-based and accept the friction. Then the fix is
      to ~/CLAUDE.md or to the hook's error message, so that a person
      hitting this is told the gate cannot see the distinction and what
      to do instead. This is a LEGITIMATE outcome -- the current
      problem is silent disagreement between two documents, not that
      the hook is necessarily wrong.

  (b) Decide from the diff. A staged diff touching only comment lines
      and string literals is mechanically decidable for Python; a
      constant change is not, and a "moved line" is not. If you take
      this route, state exactly which of ~/CLAUDE.md's listed chore
      forms you can detect and which you cannot, and make the
      undetectable ones fail closed (treated as code).

  (c) Accept a declaration from the committer. Note before choosing
      this: a gate that believes the committer's own classification is
      not a gate against the committer, only against forgetfulness.
      If you argue for it anyway, say what it still protects.

I am NOT pinning a direction. I am pinning that the answer must be
argued and that the two documents must agree when you are done.

Do NOT add an env var or flag that simply switches the attestation off.

## ITEM B -- nothing tells a user the installed hook is stale

Per U2, an installed hook can silently be months behind its generator.
The narrow fix (re-run `code-forge install-hooks`) repairs one machine
and prevents nothing.

PINNED: a user must be able to find out that their installed hook no
longer matches what this version of forge would generate, without
reading the hook. Beyond that the mechanism is yours -- a content hash
stamped into the hook and compared by `doctor`, a check inside

Weigh and state the blast radius in your reasoning: the confusing error
message is the cheap half. The expensive half is that a hook installed
before a security-relevant generator change keeps enforcing the old
rules, and the repo looks gated while running last month's gate.

## THE FOUR ITEMS

### Item A -- the hook silences the output its own message points at

This is the real defect and the only logic-bearing item here.

The generated hook runs verify with `--quiet 2>/dev/null`, then on failure
prints "See verify output above for details." Per T2 and T3 there is no
output above: stdout's reason line is suppressed by --quiet and stderr is
sent to /dev/null. The message now points at nothing.

Note what this replaced. "Run: code-forge verify" was actionable -- it told
the operator to run the command again WITHOUT --quiet, which is exactly how
you see the named file. The change followed the letter of item 5 (point at
the data, not the review) and left the operator worse off than before.

PINNED AS BEHAVIOUR, not as an implementation. After your change:

  1. On PASS the hook stays SILENT. --quiet is there for a reason; a fix
     that prints "verify: PASS -- all 7 checks passed" before every commit
     is not acceptable.
  2. On FAIL the operator sees verify's reason, including the filename
     bf44af5 produces, WITHOUT running anything a second time.
  3. Both channels are covered, not just stdout -- see T3.
  4. The hook still exits 1 on failure.

Choose the mechanism yourself. Consider and reject in one line each, in your
report: reverting the message to "Run: code-forge verify"; dropping --quiet
only; dropping 2>/dev/null only; capturing output and replaying it on
failure. If you conclude the cheapest option is right, say so with evidence
-- honest disagreement with the framing is a successful outcome.

Fix at the DEFINITION (T4), not at a use site.

Update the docstring at T6 in the same commit. A comment that describes the
old behaviour is itself a finding, and this exact file has been bitten by a
stale comment once already.

TEST OBLIGATION, and read this part carefully. A test that asserts the
generated STRING contains or omits some substring proves almost nothing --
it tests the shape of the implementation you just wrote, and it is the
classic assertion that silently checks the wrong thing. The test must fail
if the reason is discarded. The shape that achieves that: write the
generated hook to a temp file, put a stub `code-forge` on PATH that exits 1
and prints a known marker, run the hook, and assert the marker appears in
the output the operator would see. Also assert the exit code is 1. Use a
different mechanism if you have one that fails for the same reason; say
which you used and why.

INJECTION: restore `--quiet 2>/dev/null` at the definition, show the new
test FAILING, restore, show it PASSING. Paste both outputs. Injecting
anywhere other than that exact line does not count.

## SWEEP 1 -- Python version axis (server side)

Goal: turn the claim "mcp SDK requires >=3.10, and 3.10-3.14 are
identical because ping is protocol-level" into MEASURED data.

For v in 3.8 3.9 3.10 3.11 3.12 3.13 3.14:
1. Get the interpreter. 3.9 and 3.14 are already on the box
   (/usr/bin). For missing ones, install via uv (fast):
   `uv python install 3.10 3.11 3.12 3.13` (uv is the lazy path;
   if uv absent, `uv` via `pipx install uv` or pyenv -- record
   which you used). If a version genuinely cannot be installed,
   record "unavailable" -- do not fake it.
2. Make an isolated venv for that version and install the SDK:
   `<pythonX> -m venv /tmp/venvX && /tmp/venvX/bin/pip install mcp`
   Record the mcp version pip resolved (`pip show mcp`).
   EXPECT: 3.8 and 3.9 FAIL to install/import mcp (requires-python
   >=3.10). Capture the actual error -- that IS the result for
   those rows (turns the floor claim into evidence).
3. For versions where mcp installed, drive the probe with the
   SAME-version client to prove that server-python works end to
   end:
   `/tmp/venvX/bin/python .planning/evidence/send_ping_probe/ping_probe_client.py /tmp/venvX/bin/python`
   (the client's argv[1] is the interpreter used to launch the
   server; passing the venv python runs BOTH sides on version X).
   Read /tmp/ping_probe.log for the `pyX.Y ... ANSWERED in N.Nms`
   line.
Record per row: python version | mcp version | ANSWERED+latency /
FAILED(reason) / unavailable.

## SWEEP 2 -- Client axis (server fixed at 3.14)

Goal: does each real client answer a server ping. Server always
launched with system python3.14.

- C1 Python reference SDK (control):
  `python3.14 .planning/evidence/send_ping_probe/ping_probe_client.py`
  Already known ANSWERED ~1.0ms; re-run for independent confirm.
- C2 TypeScript reference SDK (proxy for Cursor/Windsurf; VS Code
  now confirmed directly by human): a node harness exists pattern
  in the README/history -- `npm i @modelcontextprotocol/sdk` in a
  scratch dir, connect a Client over StdioClientTransport to
  `python3.14 <server>`, call probe_ping. Record ANSWERED+latency.
- C3 Claude Code CLI: register the probe and trigger it headless.
  `claude mcp add ping-probe --scope local -- python3.14 <abs server path>`
  then `claude -p "Call the probe_ping tool and report its output."
  --allowedTools "mcp__ping-probe__probe_ping"`, read the log,
  then `claude mcp remove ping-probe --scope local`. (Known-good:
  answered 2.4ms earlier; independent re-confirm.) If nesting
  claude inside a claude sub-session misbehaves, record that and
  move on -- do not loop.
- C7 NEGATIVE CONTROL (discrimination check): a dumb pipe must NOT
  produce ANSWERED (it can send requests but cannot answer the
  server's ping, and EOF tears the session down first):
  `printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"pipe","version":"1"}}}' '{"jsonrpc":"2.0","method":"notifications/initialized"}' '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"probe_ping","arguments":{}}}' | python3.14 <abs server path>`
  EXPECT: the server emits a ping request line on stdout but the
  log shows NO ANSWERED line. This proves the test discriminates
  answer-capable clients from dumb pipes (so a "no ANSWERED" for a
  real client would be meaningful, not a harness artifact).

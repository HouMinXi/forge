## Why the gates (architect note, do not skip)

- SDK confirms the mechanism EXISTS: server/session.py:443
  send_ping(); shared/session.py:244 send_request
  request_read_timeout_seconds. The Python CLIENT auto-answers
  (client/session.py:589 -> EmptyResult). BUT Claude Code ships
  its own TS client -- the Python SDK's behavior is a PRIOR, not
  proof about CC.
- send_ping detects "is the transport peer alive and responding",
  NOT "does the client still want this server". The whole value
  depends on abandonment manifesting as no-answer. That is an
  INFERENCE from the schedule's narrowed leak model (a subreaper/
  pty-host holds a dup of the socket fd, so the real client is
  gone from the transport) -- unverified. T0 verifies it.
- Shipping this blind risks a regression worse than the bug: a
  false-kill hits every live review, the orphan hits a rare
  corner. Asymmetric downside = gate hard.

## T0 -- the decisive experiment (the ONLY thing to do until it passes)

Instrument a throwaway build of the server to send ONE ping to
the client shortly after the first request, log the result and
latency. Connect via REAL Claude Code (not a synthetic client).
Then, in the same real session, force the abandonment condition
the tripwire caught (e.g. the real IDE/session-restart or
failure-reconnect that produced the wild orphan) and send another
ping. Record:
  (a) healthy connection: does CC answer? within what latency?
  (b) abandoned connection: does the ping time out (good) or still
      get answered (send_ping is useless for this mode)?
Deliver the raw log. Only (a)=answered-fast AND (b)=times-out
unlocks T1+.

## T1+ -- implementation (ONLY if T0 passes)

Wiring (ground-truthed; the reason this is not free):
- low-level Server.run (lowlevel/server.py:640) enters lifespan
  (657) BEFORE creating ServerSession (659). The session is a
  request-scoped local via contextvar; FastMCP lifespan gets only
  `self` and cannot reach it.
- The pinger must capture the session from the FIRST request
  context (stash in a module global) or wrap the low-level run.
  Until the first request arrives there is no session to ping --
  acceptable: a server abandoned before any request still gets
  EOF on a clean disconnect; only fd-leak-before-first-request is
  uncovered, and that is vanishingly rare.
- Background task: every ping-interval, send_ping with
  request_read_timeout_seconds; on timeout -> cleanup_all -> exit
  (reuse the 38.1 shutdown path, do NOT reinvent it). Interval and
  timeout are named constants with a comment (detection latency =
  interval; set from T0's measured healthy latency, not guessed).
- Coexist with PDEATHSIG: parent-death is still caught by 38.2
  first (faster, kernel-level). send_ping only adds the
  parent-alive path. Verify the two shutdown triggers do not race
  into a double cleanup_all (idempotency of cleanup_all).

CRITICAL DESIGN -- Parser return contract (addresses Consensus #4):
- Empty string input -> return `[]` (tool produced no output, treat as clean)
- Valid output with findings -> return `[Finding, Finding, ...]`
- Valid output with zero findings -> return `[]`
- Non-empty but unparseable output (corrupt JSON, wrong structure) -> return `[ToolError(tool_name=tool_name, exit_code=exit_code, stderr="", message="Failed to parse {tool_name} output: {error}")]`
  NOTE: parsers set `stderr=""` because they only receive stdout. The CLI layer (Plan 04
  step f) enriches ToolError.stderr with the tool's actual stderr captured by run_tool
  (Round 5 R5-M3). Parsers must NOT attempt to access stderr.
- This means downstream code MUST check for ToolError in the results list. A non-empty list with ToolError items means tool failure, not findings.

1. `src/forge/parsers/shellcheck.py` -- `parse_shellcheck(output: str, tool_name: str = "shellcheck", exit_code: int = 0) -> list[Finding | ToolError]`:
   - Return [] on empty string
   - `json.loads(output)` to get array of findings
   - Map each item: file=item['file'], line=item['line'],
     end_line=(item.get('endLine') or item['line']),
     column=item.get('column', 0), rule_id=f"SC{item['code']}",
     level=item.get('level', 'warning'), message=item['message'],
     tool_name=tool_name, fix=None
   - IMPORTANT (Round 3 H-1 -- JSON null gotcha): Use `(item.get('endLine') or item['line'])`
     instead of `item.get('endLine', item['line'])`. The `.get(key, default)` pattern returns
     None when the key exists but has a JSON null value, which then crashes on int operations.
     The `or` pattern falls through to the fallback on both missing keys AND null values.
     Apply the same pattern everywhere a JSON field might be null.
   - On JSONDecodeError or KeyError for required fields: return [ToolError(...)] using the passed-in exit_code

2. `src/forge/parsers/ruff.py` -- `parse_ruff(output: str, tool_name: str = "ruff", exit_code: int = 0) -> list[Finding | ToolError]`:
   - Parse SARIF 2.1.0 JSON. Iterate runs[].results[].locations[]
   - Strip `file://` prefix from artifactLocation.uri.
     Round 7 R7-L1 (Kimi): the parser does NOT relativize absolute paths to repo root.
     Rationale: parsers are pure functions with no I/O and no knowledge of cwd; pulling
     `os.getcwd()` or repo-root detection into parsers would break testability and
     introduce hidden coupling. SARIF tools are configured to emit paths relative to
     the working directory by their own conventions (ruff/semgrep do this by default).
     If a tool emits absolute paths, they are stored verbatim in Finding.file; the
     reporter layer (Plan 04) is responsible for any presentation-time relativization.
     This boundary is explicit and tested: a SARIF input with `file:///abs/path/x.py`
     yields `Finding.file == "/abs/path/x.py"`, not a CWD-relative path.
   - Map region fields: startLine, endLine (default to startLine), startColumn (default 0)
   - IMPORTANT (Round 3 H-1): Use `(region.get('endLine') or region.get('startLine', 0))`
     for endLine, not `region.get('endLine', region.get('startLine', 0))`. JSON null values
     from SARIF must not produce None -- fall through to startLine.
   - On JSONDecodeError, KeyError, TypeError, or AttributeError during field extraction:
     return [ToolError(...)]. The except clause MUST catch all four -- JSONDecodeError
     for corrupt JSON, KeyError for missing required fields (e.g., artifactLocation.uri
     absent from a valid-but-incomplete SARIF), TypeError for unexpected None values in
     nested access (e.g., region is None), and AttributeError for non-dict values where
     .get() is called (e.g., a SARIF result entry is a string instead of a dict).
     This ensures any corrupt-but-parseable SARIF produces ToolError, not an unhandled
     exception (Round 4 R4-D1, Round 5 Mimo H-2).

   - Factor shared SARIF parsing into a function (DRY). Both ruff and semgrep use standard SARIF 2.1.0. Create `parse_sarif(output, tool_name, exit_code)` that both wrappers and PARSER_DISPATCH use. Name has NO leading underscore because it is exposed via PARSER_DISPATCH (a public API surface). Round 6 R6-C1 (DeepSeek): private-named function in public dict is inconsistent -- rename to `parse_sarif` for naming consistency with other PARSER_DISPATCH entries (parse_shellcheck, parse_clippy, etc.).
   - Round 9 R9-L2 (DeepSeek) -- physical file location: `parse_sarif` lives in
     `src/forge/parsers/sarif.py` (a NEW module file). `ruff.py` and `semgrep.py`
     each do `from forge.parsers.sarif import parse_sarif` and wrap it. The

4. `src/forge/parsers/clippy.py` -- `parse_clippy(output: str, tool_name: str = "clippy", exit_code: int = 0) -> list[Finding | ToolError]`:
   - cargo --message-format=json emits one JSON object per line
   - Filter lines where parsed JSON has "reason":"compiler-message" and message.level in ("warning", "error")
   - Guard against empty spans: if `message.get("spans")` is falsy (empty list or missing),
     skip the diagnostic (no file location to report). Only extract from spans[0] after
     confirming `len(spans) > 0`. This prevents IndexError on diagnostics that have no
     source location (e.g., top-level "aborting due to N previous errors" messages).
   - Extract from message.spans[0]: file_name, line_start, line_end, column_start.
     Round 6 R6-C2 (DeepSeek): wrap the field extraction in `try/except (KeyError, TypeError)`
     so that a span object missing any required key (corrupt cargo output, future schema
     change, or non-dict span entry) skips that diagnostic rather than crashing with an
     unhandled exception. The except branch may optionally emit a single ToolError to
     surface corruption, but MUST NOT raise. This mirrors the SARIF parser's defensive
     extraction (Round 5 Mimo H-2).
   - rule_id from message.code.code (e.g. "clippy::needless_return"). Guard against
     message.code being None (some diagnostics lack a code): skip or use rule_id="unknown".
     Same `try/except (KeyError, TypeError, AttributeError)` guard applies here.
   - Skip lines that fail JSON parse (non-diagnostic lines)
   - If ALL lines fail JSON parse and input is non-empty: return [ToolError(...)]

5. `src/forge/parsers/checkpatch.py` -- `parse_checkpatch(output: str, tool_name: str = "checkpatch", exit_code: int = 0) -> list[Finding | ToolError]`:
   - Parse line-by-line: regex `^(.+):(\d+):\s+(WARNING|ERROR|CHECK):(\S+):\s+(.+)$`
   - Map: file=group(1), line=int(group(2)), end_line=same, column=0, rule_id=group(4), level=group(3).lower(), message=group(5)
   - Skip summary lines (starting with "total:")
   - Non-empty input with zero regex matches AND no summary line: return [ToolError(...)]

6. `src/forge/parsers/non_ascii.py` -- `parse_non_ascii(output: str, tool_name: str = "non_ascii", exit_code: int = 0) -> list[Finding | ToolError]`:

   - regex: `^(.+?):(\d+):(.+)$`
   - rule_id="NON_ASCII", level="error", message=f"non-ASCII character found: {content.strip()}"

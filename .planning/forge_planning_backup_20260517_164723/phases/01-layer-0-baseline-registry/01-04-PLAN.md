
   - `determine_verdict(delta_findings: list[Finding | ToolError]) -> Verdict`:
     - If list is empty: return ("PASS", EXIT_PASS)
     - If list contains ANY ToolError items: return ("FAIL", EXIT_FAIL)
       - This addresses Consensus #4: tool crash = FAIL, not false PASS
       - A ToolError means a tool failed to run. This is a FAIL because we cannot guarantee no violations exist if the tool crashed.
     - If list contains only Finding items (non-empty): return ("FAIL", EXIT_FAIL)
     - Pure function. Per GATE-01 (Phase 1 implements PASS/FAIL only, HOLD is Phase 2+).
     - Per GATE-04, all Layer 0 violations are gate-blocking (no advisory in Phase 1).
     - Self-review followup -- optional-tool ToolError contract: `determine_verdict`
       only inspects `delta_findings`. Optional-tool ToolErrors are removed from
       `all_findings` by CLI step g and routed to `tools_failed_errors` BEFORE
       `filter_delta` runs, so they CANNOT reach `delta_findings` and therefore CANNOT
       cause FAIL. Only required-tool ToolErrors stay in the filtered list, pass
       through `filter_delta` (ToolError items always pass through line filtering --
       see Plan 03), and land in `delta_findings` to trigger FAIL. This is the
       intended behavior: optional tool failures degrade observability but do not
       block commits; required tool failures block. The contract is enforced jointly
       by step g (Plan 04) and filter_delta's pass-through rule (Plan 03).

   - `_sanitize_external_text(text: str | None, max_len: int) -> str` (private helper,
     also imported by reporter -- single source of truth, addresses self-review-R2
     SR2-7 duplication risk):
     - If `text` is None or empty: return `""`
     - Strip ANSI CSI sequences via `re.sub(r"\x1b\[[0-9;]*[a-zA-Z]", "", text)`.
       Self-review-R2 SR2-5 KNOWN LIMITATION: this does NOT strip OSC sequences
       (`\x1b]...\x07` for clipboard/title manipulation). External tools rarely
       emit OSC; if they do, output passes through verbatim. Phase 2 may extend
       coverage if a real case appears.
     - Strip control chars via `re.sub(r"[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]", "", text)`.
       NOTE: tab (\x09), LF (\x0a), CR (\x0d) are intentionally NOT stripped here;
       they are handled by the newline replacement next.
     - Replace newlines (LF/CR/CRLF) with " | " for single-line storage:
       `text.replace("\r\n", " | ").replace("\n", " | ").replace("\r", " | ")`
     - Truncate to `max_len` characters (Python str slice -- character count, NOT
       bytes; safe for multi-byte UTF-8). Self-review-R2 SR2-D4: explicit
       character-based truncation prevents the byte-slice UTF-8 corruption pitfall.
     - If truncated, append "..." (3 chars) AFTER the slice. The total result may
       therefore be `max_len + 3` chars in the truncated case -- this is acceptable
       (callers size their fields with margin).
     This helper is imported by reporter.py with `from forge.state import _sanitize_external_text`
     (Python permits cross-module access to underscore-prefixed names; convention is
     to limit such imports to within the same package, which forge.* satisfies).
   - `_sanitize_tool_error_dict(d: dict) -> dict` (private helper):
     - Returns a NEW dict with the same keys as input
     - For `stderr` field: applies `_sanitize_external_text(d.get("stderr", ""), max_len=1000)`.
       Self-review-R2 SR2-D2: uses `.get(..., "")` defensively so a malformed input
       dict missing the `stderr` key does NOT raise KeyError.
     - For `message` field: applies `_sanitize_external_text(d.get("message", ""), max_len=500)`.
       Self-review-R2 SR2-11: parser-generated messages are nominally controlled,
       but a defensive cap prevents surprise blowups from future parser changes.
     - For other fields (tool_name, exit_code): copied verbatim
     - Input dict is NOT mutated (returns a new dict)

     calls `_prepare_state_dir(state_path)` first (creates dir + writes .gitignore idempotently, R9-L3), then uses tempfile + os.replace pattern from cli/file_utils.py atomic_write (reimplemented, not imported per D-01).
     If `tools_failed_errors` is provided (non-None and non-empty), serialize and

     ```python
     if tools_failed_errors:

             name: [_sanitize_tool_error_dict(e.to_dict()) for e in errs]
     ```

     ```python

                                       delete=False) as f:

     ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User input -> diff_spec | CLI argument validated by git.py before use |
| External tools -> forge | Tool stdout parsed by forge parsers; ToolError on crash |
| Forge -> filesystem | State written to .forge/state.json via atomic write |
| tools.yaml -> registry | User-editable config could contain malicious commands |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-11 | Tampering | cli.py diff_spec | mitigate | CLI passes diff_spec to run_git_diff() which calls validate_diff_spec() -- rejects flag injection and metacharacters. |
| T-01-12 | Tampering | cli.py git subprocess | mitigate | CLI does not call git directly. All git calls go through forge.git module which never uses shell=True. |
| T-01-13 | Information Disclosure | state.py | accept | state.json contains file paths and violation messages. Expected behavior for a local development tool. No secrets written. |
| T-01-14 | Tampering | tools.yaml malicious command | accept | tools.yaml specifies commands that forge executes via subprocess. A malicious tools.yaml could run arbitrary commands. However, tools.yaml is a local user-editable config -- if the user's config is compromised, their system is already compromised. Document this trust assumption. |
</threat_model>

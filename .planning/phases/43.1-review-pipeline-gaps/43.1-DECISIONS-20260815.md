Ground: verify.py scopes every receipt check to the attested window.

and the excerpt checks filter `if r.get("cycle") in last_n` with a

not fail the gate when required_cycles is low). Nothing further to
write -- the contract is documented in the two places a cold session
looks: the commit message and the code comment. Charter backlog entry
moves to resolved-by-0309c55.

## C5 (gate.yaml timeout reaches mutation baseline): RESOLVED for the main path; one intentional split remains, now documented

Ground: machine.py:440 reads `test_config.get("timeout_seconds", 120)`
from the worktree gate.yaml and passes it through
launch_detached_mutation -> the detached child -> run_mutation ->
_run_baseline_guard(timeout=baseline_timeout). Introduced by 8f745dd
("mutation: make the gate actually measure something"), whose message
answers the charter's design question directly: the baseline timeout
"reads test.timeout_seconds from gate.yaml instead of a hardcoded 120
that bore no relation to the suite it was timing."

Decision: the charter asked whether L2's flaky-guard budget should
equal L1's correctness budget. The answer landed as YES, with a reason:
the baseline runs the same test command the gate configures, so its
budget should be the suite's own budget. The old hardcoded 120 was
either too short (this repo's suite runs 120-900s, so the baseline
timeout advisory fired constantly under contention) or arbitrary. The
contract is recorded in the commit message; nothing further to change
on the main path.

Remaining split, now intentional: fixval.py:277 calls
_run_baseline_guard without a timeout, taking the 120 default. That is
a different consumer -- it baselines a scoped candidate
(test_cmd + candidate.test_files), not the full suite, so a short
flaky-guard budget is appropriate. Recorded here as intentional; if a
future fixval case starts timing out its baseline, thread
timeout_seconds through that call site rather than raising the default.
(Optional follow-up: one comment line at the fixval call site stating
this split, so the next reader does not re-derive it.)

## Charter 6 (check 6 coverage-floor intent): DECISION RECORDED, needs user sign-off

Ground: check 6 (verify.py:726-733) requires the union of a cycle's
excerpt-covered lines to reach 60% of all changed lines, where
`all_diff` includes every line of every changed file, test files
included. `_excerpt_covered` credits only lines the excerpt content
actually shows (the "pasted three lines, earned 1000" hole is already
closed). The floor's stated role (verify.py:656) is to mitigate STEP
C's known limitation: content checks cannot tell "covers only context
lines" from "covers actual changed lines", and check 7 (Jaccard) only
catches cross-cycle repetition, so check 6 is the absolute-quantity
half of the anti-rubber-stamp pair.

The charter's observation stands: on a diff that is 83% new test code,
clearing 60% structurally requires quoting test bodies near-verbatim.

Two readings:

(a) Working as intended. The floor measures review quantity, not
    review quality, and that is true for implementation lines too --
    the test-heavy diff is not specially penalized, it just makes the
    trade visible. Forge's own doctrine says test diffs deserve the
    STRICTEST review (bug-injection is the project's proof-of-test rule;
    a test that exercises broken code publishes the bug's location).
    A lower bar for test lines would run against that doctrine.

(b) Miscalibrated. The floor is gamed by pasting, and pasting test
    bodies is easier than reasoning about them. On test-heavy diffs the
    floor buys verbatim transcription, not understanding, while making
    the diffs the project wants more of the most expensive to attest.

Recommendation: (a), with two cheap additions. First, write the intent
into the check-6 comment (one sentence: the floor deliberately includes
test lines because tests are review objects, not review scaffolding).
Second, if the verbatim-paste concern is worth acting on, that is a new
measurement (per-hunk witness already exists as STEP A; a per-file
witness or excerpt-diversity signal would be the next increment), not a
recalibration of 60% -- scope it as its own item rather than folding it
into this decision.

### External practice survey (exa web search, 2026-08-15)

The survey sharpened the decision; the key finding is that two different
things share the word "coverage", and the industry consensus differs
between them.

Test-execution coverage (Codecov patch coverage, Azure DevOps diff
coverage, Chromium CodeCoverage-1): the denominator counts changed
PRODUCTION lines, and the consensus is 60-80% on the diff. Chromium
explicitly excludes test files from that denominator by path
("Tests are evidence, not the covered product surface") and offers a
Low-Coverage-Reason footer with named categories (TRIVIAL_CHANGE,
HARD_TO_TEST, LARGE_SCALE_REFACTOR, ...) as the escape hatch instead of
lowering the number.

Review-evidence coverage (forge check 6): the denominator counts lines
the REVIEWER must have quoted. Google's eng-practices is the direct
doctrine for this half: "Tests do not test themselves, and we rarely
write tests for our tests -- a human must ensure that tests are valid",
"Will the tests actually fail when the code is broken?", and the SWE
book's "a test should be obvious upon inspection. Because there are no
tests for the tests themselves, they require manual review as an
important check on correctness." Reviewers are expected to review tests
and feature code alike, and blocking a change for missing tests is
explicitly reasonable.

Two survey findings adjust the (a) position without flipping it:

1. Google's SWE book warns that a fixed numeric bar becomes a ceiling:
   "instead of treating 80% like a floor, engineers treat it like a
   ceiling. Soon, changes begin landing with no more than 80% coverage."
   Google's own answer is no global threshold plus voluntary alerting
   levels. For forge this argues for keeping 60% as-is while making the
   failure actionable: the check-6 message reports only a percentage
   ("coverage 42% < 60%"); listing the uncovered files/lines would push
   the reviewer toward the gap rather than the number.

2. The industry-standard relief valve for structurally expensive diffs
   is NOT recalibration -- it is an explicit, named-reason exemption
   (Chromium's Low-Coverage-Reason). If forge ever wants to relieve
   test-heavy or trivial diffs, the precedented shape is a
   per-run reason field with fixed categories, not a lower number for
   test lines. That keeps the default honest and the exception visible.

SIGNED OFF 2026-08-15 by user: (a), with all three additions:
(1) intent comment in verify.py check 6, (2) actionable failure message
listing uncovered files, (3) the Chromium-style exemption mechanism
(review-reason footer with named categories) filed as a backlog item,
not implemented now. The 60% number itself does not change, and test
lines stay in the denominator.

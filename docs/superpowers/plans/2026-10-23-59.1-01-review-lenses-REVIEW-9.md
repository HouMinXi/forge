## §P2-1 (closed)

1. **q_hi and q_lo use the same definition.** Both come from the same 5,000 entry-clustered resamples (seed 591), as the 20th and 80th percentiles, and both use numpy.percentile's default linear interpolation (PLAN :324, spec :396). Both sides take the conservative end: the null uses q_lo, the tooth uses q_hi, and both use λ_lo. The tooth gets weaker as λ falls (for example at q 0.6, λ3 gives 0.216 and λ2 gives 0.374), and the null rises as λ rises, so λ_lo is conservative for both sides.
2. **The 2×SE arithmetic is correct.**
   - null: sqrt(0.9·0.1/1e4) = 0.0030, so 0.90 + 0.006 = 0.906.
   - tooth: sqrt(0.2·0.8/1e4) = 0.0040, so 0.20 − 0.008 = 0.192.
   - Φ(−2) = 0.0228, so "about 0.023" holds under the normal approximation. The small effect of rounding to three decimals is in note A2.
3. **Seed stability.** Using the pilot seeds (tooth 520–529, null 500–509), I ran 10 seeds on each of the old edge cells, 10,000 trials per cell, N = 150:

## §N3 judgment: listing the residual risks plus a human checkpoint is enough; a hardened gate is not recommended

- **Threat model.** The risk is an executor agent that advances automatically. Task -1 is `checkpoint:human-verify` with `gate="blocking"`, the PLAN sets `autonomous: false`, and the resume-signal must be "admitted", typed by forge. The only way an executor can get past the checkpoint is by ignoring the checkpoint itself, and an executor like that would ignore any script result in the same way. So the script is a fail-closed syntactic pre-screen, and the semantic judgment belongs to a human anyway. The remaining bypasses ("withdrawn", "deferred indefinitely", a refusal written on a continuation line, and so on) all require the admission text itself to be written adversarially. The admission text is a docs-only change that forge approves personally, and forge reads exactly that text at the checkpoint, so the chance of exploitation is low. The reruns of the script in Task 0 and Task 10 add one more layer against syntax errors.
- **The cost of a hardened design.** One option is a positive allowlist or explicit marker (for example, requiring the LENS line to carry "Admitted YYYY-MM-DD by forge"). That would tie the plan to the format of an admission text that has not been drafted yet: when forge writes the admission the normal way it would be wrongly rejected, and the outcome would be changing the admission text to suit the script, which is backwards. The other option is to keep extending the blacklist (withdrawn, superseded, ...). That is whack-a-mole and also adds false rejections, for example for legitimate wording such as "supersedes 59-06".
- **Conclusion.** Keep it as is. The residual risks are listed item by item in the Task -1 acceptance (:153) and spec :342, and are explicitly handed to forge's checkpoint. That is the right division of labor.

## Non-blocking notes (not counted as findings)

- **A1 (wording of the JSON fields).** PLAN :324 and spec :396 say "always prints one JSON verdict (inputs, clamped q values, N, trials per cell, both thresholds, numpy/scipy versions, every cell)". The full field set holds only on the success path and the "no qualifying R" path. The `_fail` path (rc 2, rc 3, and the rc 0 cases of q_lo out of range, λ_lo < 0.5 and a version mismatch) has only computable, chosen_R, reason and argv, and on a version mismatch the versions appear only in the reason string. With scipy missing it is an rc 1 traceback with no JSON. None of this affects the verdict, because the rules go by exit code and computable, and (v) also covers non-zero exits. Optional fix: change the wording to "rc 0/2/3 all print JSON; the full fields appear only after the inputs pass the checks", or also output `versions` in `_fail`.
- **A2 ("about 0.023" is really about 0.03).** run() rounds the pass rate to three decimals (:138), so the effective thresholds are X ≤ 1924/10000 (1925 rounds to 0.193) and X ≥ 9056/10000 (9055 rounds to 0.905). When the true value sits exactly on the target, the single-cell pass probabilities are binom.cdf(1924; 1e4, 0.2) = 0.029 and binom.sf(9055; 1e4, 0.9) = 0.031, not 0.023. The order of magnitude and the conclusion do not change, and the tooth needs both k values to pass at once, so the joint probability is smaller still. Optional: change the wording to "about 0.03".
- **A3 (Task 11 checks only the last commit).** `HEAD~1 HEAD` covers only the last commit. If the slice breaks the "one signed commit" rule by adding a ROADMAP-changing commit before it, the check passes (tested: rc 0). The PLAN already says there is only one commit, the executor does not commit, and it does not commit task by task, so this is not a defect. Optional hardening: record HEAD at the time Task -1 passes as BASE, switch to `git diff --quiet "$BASE" HEAD -- ...`, and add `test "$(git rev-list --count "$BASE"..HEAD)" -eq 1`. Also, the whole sentence must be on one line: wrapping at 72 columns fails closed, and so does Task 9's grep on COMMIT_MSG.txt, so the hygiene section could carry a reminder.
- **A4 (cells inside the threshold band).** The true value of R3 λ1 q0.35 is about 0.19–0.195, and 1 of 10 seeds passes. This is inherent to cells inside the band, and the 2 SE margin does not promise stability inside the band. Optional: add one sentence to the PLAN, "for a cell whose true value falls in 0.184–0.200, the verdict may vary with the seed, but its true value is below the 0.20 target".
- **A5 (monotonicity of the null in q).** "the null pass rate falls as q falls" holds near the threshold (low λ). It is not strict in high-λ cells, for example R7 λ2 gives 0.972/0.979/0.962, but those cells are far above 0.906 and do not affect the verdict.
- **A6 (computable range of b).** The computable range is roughly λ_lo ≳ 1 and q_hi ≲ 0.4. When the 59.1-02 PLAN is pre-registered, I suggest writing this down as "may be not computable, as expected", so it is not read as a failure after the fact.
